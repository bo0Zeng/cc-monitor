# 功能计划 — B03 驾驶舱 + B04 settings.json 钩子诊断

> B03 依赖 B02（`cc-spawn` 收编）。B04 与两者正交，写在一起是因为它们同属"cc-monitor 认识 cc-bus"这件事。

## 0. B03 的两条硬约束（先说清楚，它们决定了方案形状）

**约束一：不新增轮询（红线）。** cc-bus 的状态全在 aya 本机 `~/.cc-bus/`，而 cc-monitor 跑在
Windows、只能经 SSH 看。两条备选：复用 daemon 既有 inotify watcher（**违反 daemon 零改红线**，
且要新增协议帧）；或**按需刷新**。→ 取按需刷新。

**已有现成范式，照抄不另发明**：`src-tauri/src/mcp.rs::read_remote_mcp_servers`
——用户在设置页点开 MCP 分节时才 `connect_and_exec_cmd` 一条**定值** `cat` 命令读远端 dotfile，
宽容解析（缺/坏 → None），30s 超时 + 32MB 上限，大解析进 `spawn_blocking`。
前端 `settings/mcp-section.ts:300` 在**打开分节**时 invoke 一次。B03 逐条对齐这个形状。
（同 F10 用量探针的懒加载精神：重操作只在用户真的要看时才做。）

**约束二：`cc-spawn` 图形化必须建立在 B02 之上。** 否则等于在 cc-monitor 侧再造第四套起会话
实现——亲手制造本工作区刚消灭的病（账本 K8）。B02 没落地前，B03 只做**只读**部分。

## 1. 盘面实测：这些状态文件**不干净**，读它们必须防御性解析

2026-07-28 直接看了 `~/.cc-bus/`，发现三类脏数据。**这不是假想风险，是现状**：

| 现象 | 实例 | 对 B03 的含义 |
|---|---|---|
| **陈旧登记** | `agents.tsv` 里最早的条目是 `2026-07-18`（10 天前），进程早不在了 | 登记 ≠ 在线。必须与"进程是否真在"分开呈现，否则驾驶舱会列一堆幽灵 |
| **TSV 被内嵌换行破坏** | `spawned.tsv` 有一行是 `x_y_cc\t/tmp/tmp.o6LGcLq9Qq/x⏎y\t...`——目录名里含换行，把一条记录劈成两行 | **按行 split 会解析出畸形记录**。必须容忍并跳过，不能让一条坏数据把整个面板搞崩 |
| **垃圾 id** | `inbox/` 里有 `--help.jsonl`、`282.jsonl`——有人敲了 `cc-send --help`，把 `--help` 当成了收件人 | id 不可信，渲染前要过一遍字符集；也说明 cc-bus 自己的入参校验有洞（**记录，但不在本功能修**） |

→ **DoD 里必须有一条"喂脏数据不崩"的测试**，用上面三个真实样本当输入。

## 2. B03 DoD（分两批，第二批依赖 B02）

### 批一：只读驾驶舱（不依赖 B02，可先做）
- [ ] 新增 Rust IPC `read_cc_bus_state(origin)`——**照 `read_remote_mcp_servers` 的形状**：
      定值命令（零用户输入拼接 → 零注入面）、超时 + 大小上限、宽容解析、只读。
      一次读回 `agents.tsv` + `spawned.tsv`（一条命令 `cat` 两个文件，用分隔标记切开，省一次往返）。
- [ ] 防御性解析：字段数不足/id 字符集非法/时间戳解析失败 → **跳过该行并计数**，不抛。
      解析结果带一个 `skipped: number`，UI 如实显示"N 条无法解析"而不是假装干净。
- [ ] UI：设置页新增「cc-bus」分节，**打开分节时才 invoke 一次**（不在应用启动时预取）。
      列出：agent id / 工作目录 / 登记时间 / 是否 spawn 的（来自 `spawned.tsv`）。
- [ ] **"登记"与"在线"分开呈现**：`agents.tsv` 只证明它登记过。要判在线需另查 tmux
      （`tmux has-session`），那是**第二次往返**——放在用户点某一行的"检查"上，不默认全量查。
- [ ] 手动"刷新"按钮（同 F10 用量探针的 `force`）。**无 `setInterval`、无后台定时任务。**

### 批二：派活 / 读 inbox / 图形化 spawn（**必须在 B02 之后**）
- [ ] 给某个 agent 发消息 = 远端跑 `cc-send <id> "<text>"`（经既有 launch 路径，不另造）
- [ ] 读某个 agent 的 inbox = `cat ~/.cc-bus/inbox/<id>.jsonl`，同样定值命令 + id 过字符集
- [ ] 图形化 spawn = 调收编后的 `cc-spawn`（它内部已改经 `ccm`）——**不在 cc-monitor 侧重写起会话**

**不做什么**：
- **不**在 cc-monitor 侧实现 cc-bus 的投递管线（ACL/限流/去重/灭环）——那是 `cc-bus-lib.sh` 的活
- **不**做实时消息流（要么轮询要么长连，两条都违反约束一）
- **不**替用户装/改 cc-bus 的钩子（那是 B04，且只读+生成）

## 3. B04 DoD：settings.json 钩子的读 + 诊断 + 生成待贴文本

用户 2026-07-28 定调：**不写** `~/.claude/settings.json`。cc-bus 自己的安装脚本第 3 行
同样拒绝改它（"只做可逆的本地安装：不改全局 settings.json、不 systemctl"）——**两边一致，不是我的保守**。

- [ ] 读 `~/.claude/settings.json` 的 `hooks` 段（远端与本机两侧；解析失败宽容降级）
- [ ] 诊断 cc-bus 需要的两个钩子是否装好：`SessionStart` → `cc-register`、`Stop` → `cc-bus-stop-hook`
- [ ] 三态如实呈现：**已装 / 未装 / 装了但指向别的路径**（第三态最容易被误报成"已装"）
- [ ] 生成待贴 JSON 片段 + 一键复制（同 F08 别名生成器的既有形状）
- [ ] **绝不写入**。文案里说清"请自己粘贴"，并说明为什么不代劳（这是共享的全局配置，
      cc-monitor 不该单方面改它）

## 4. 测试策略

- Rust 侧解析器纯函数化后单测：喂 §1 那三个**真实脏样本**（内嵌换行行 / `--help` 这种垃圾 id /
  10 天前的陈旧条目），断言不 panic、坏行被跳过并计数、好行仍被解出。
- 定值命令的零注入面：断言命令串里不含任何来自 `origin` 之外的插值
  （同 `mcp.rs` 那条 `CMD` 常量的形状）。
- UI 侧：断言**不存在** `setInterval`/后台定时器（守红线，用 grep 断言 + code review）。
- B04：三态各一条测试，重点是第三态（指向别的路径）不能被误判成已装。
