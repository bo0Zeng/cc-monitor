## 流程一：新用户（Linux —— 用户这台就是）

| 步 | 他做什么 | 实际会发生什么 | 判定 |
|---|---|---|---|
| 1 | 读 README 决定装不装 | **「系统要求：Windows 11 / 10 (1809+)」** —— 安装章节**一个字没提 Linux**，尽管 v3.4.0 就首发了 `.deb`（README 抬头的版本流水账里提了，安装章节没有） | ★**卡死**。Linux 新用户读到这行就走了 |
| 2 | 去 Releases 页找 | `.deb` 在 ✓。但资产里还有个 `monitor.exe`，而 README 说「文件名形如 `cc-monitor_<version>_x64-setup.exe`」 | ⚠ 名字对不上 |
| 3 | 校验 SHA256 | `SHA256SUMS-linux.txt` 里**列了 `monitor`（Linux 裸二进制）的 hash，而那个文件根本没上传**（Linux job 的 `files:` 只有 `*.deb` + 校验和） | ★**校验和指向一个不存在的资产** |
| 4 | `dpkg -i` 之后敲什么 | 装出来的可执行叫 **`monitor`**（`mainBinaryName` 未设 ⇒ 用 cargo 包名），而 README「首次使用」第 1 步写「启动 **cc-monitor.exe**」 | ★**照文档找不到程序** |
| 5 | 用远端功能 | 加机器 → daemon 自动部署（内嵌 musl 二进制经 SFTP 推）| ✅ **这条链是完整的** |
| 6 | 用本机 `cc` / `cct` | **零入口**（开放-6）。三个受管工具没有一个能装到本机 | ★ |

## 流程二：旧版本用户（装新版覆盖）

| 组件 | 会不会跟着更新 | 依据 |
|---|---|---|
| app 本体 | ✅ | `.deb` / `.msi` 覆盖安装 |
| **远端 daemon** | ✅ **自动** | 连上后比 `build_id`，不符 → `StaleBuild` → 自动重新部署（`ssh_source.rs:1920/1929`） |
| **远端 `ccm`** | ★ **永不自动更新，且无任何过期提示** | `sftp.rs` 里**零个** `CCM_VERSION` 引用 —— 与 daemon 那套 `StaleBuild` 判据形成鲜明对照。要手动去**每台**机器卡片重点一次「装 ccm 助手」，**而没有任何东西告诉你该点** |
| 本机 `ccm` / `cc-bus` / `cc-acct-iso` | ★ 全不动 | 开放-6 |

### 远端 ccm 这条是本次走查最值钱的发现

它与开放-6（本机 ccm）**是同一个病**，但影响面更大：**每一个有远端机器的用户都中**。
症状与用户报的那个一模一样 —— 远端上跑的 `cct` 停在装它那天的版本，此后所有 ccm 修复
（`-cc` 后缀反转、`--detach`、账号继承、无条件避让）都收不到，而 app 从不提示。

**原料是现成的**：`ccm --ccm-probe` 会打 `version=<CCM_VERSION>` 与 capabilities 行
（实测：仓里 `version=2` + 带 `detach,tmux-size`；用户机器上 `version=1` + 不带）。
app 已经在跑这个探针（`ccm_cli_has_required_elements` 那套守卫就基于它），**只是没人比对**。

⚠ **但 `CCM_VERSION` 单独不够**：它是**能力协议版本**，只在能力变动时 bump。
不改变能力面的修复（`666cc14` 那条 attach 修复就是）不会让它变。⇒ 判据要用**内容指纹**。
