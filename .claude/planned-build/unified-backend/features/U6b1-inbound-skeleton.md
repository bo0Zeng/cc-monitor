## Phase B 摸底：实测，不采信计划的叙述

U6a 的四个计划数字全被机检推翻，所以这一轮开工前先逐条量。**三处与计划的叙述不同：**

| 计划怎么说 | 实测 | 判定 |
|---|---|---|
| 「双向 wire」听起来是从零加入方向 | **入方向已经有一条**：`--resolve` 是一次性 exec，**读 stdin** 的 `ResumeSpec` JSON（`control/resolve_query.rs`，走 stdin 而非 argv 是因为 `launchCandidates` 可多条、避 argv 长度限）。缺的是**流式连接上**的入方向 | 起点不是零，是「有 RPC、无常驻通道」 |
| （未提载体） | `src-tauri/src/ssh_source.rs` 里 **`stdin` 零命中**；连接拿的是 `russh::ChannelStream<client::Msg>`，**双工**。⇒ 入方向的载体**现成且完全没人用** | 不需要新开连接/端口 |
| 「argv 三分」像是给现有分类加一档 | 今天是**二分**：`split_stream_flags` 剥掉 `--with-bg` / `--tail-only`，**剩下非空即一次性查询**。第三类（子命令自己的选项，如 `--scope` / `--limit` / `--accts-dir`）从没进过这张表 | 「三分」是重建分类，不是加一档 |

### 入方向缺失**已经在制造绕路**（这是做它的实证，不是推测）

- **`--tmux-notify` 存在的唯一理由**就是 hook 子进程没法给正在跑的 daemon 发消息 ——
  只能新起一个进程、校验身份、发 `SIGUSR1`。`main.rs` 里那段注释自己写着这是「hook 子进程走的通路」。
- **`--resolve` 为一次极小的 RPC 单开一整条 SSH exec**。它的入参小到用 stdin 只是为了避 argv 长度限。
- 两者都是「没有常驻入方向」的代偿。

### 现有出方向的形状（入方向要对称，先量清）

| 项 | 实测 |
|---|---|
| 通道 | `observe/watcher.rs::CHANNEL_CAPACITY = 10_000`，`mpsc::channel::<Frame>` |
| 背压 | reader 用 `try_send`；满则丢帧并计数，排空后发一次 `Overflow { dropped }`（#32） |
| 写出 | `writer_task` 单 task 排空通道写 stdout；broken pipe 视为正常寿终 |
| 线约束 | 每行恰一个 UTF-8 JSON 对象、`\n` 结尾、对象内无裸换行 |
| 握手 | `Hello` 是**首帧**，在任何别的东西之前 flush |

## 本功能的边界（U6b 拆三件，这是第一件）

U6b 原列九项，装不进一份计划（skill 的粒度准则：一份计划讲得清、几步做得完、DoD 可独立验收）。
按**承载关系**拆：

| 件 | 内容 | 为什么这样切 |
|---|---|---|
| **U6b-1（本件）** | 流连接上的**入方向骨架**：行协议 + 请求信封（`id`）+ 应答/错误形状 + 取消 + 入方向背压与大小上限 + 两条机检（Hello 前不许有 stdin · 命令处理器不许跑在流线程上） | 后两件全都骑在它上面。**先把信封和线程纪律钉死**，否则后面每加一条命令都要重谈一次 |
| **U6b-2** | 能力协商扩到入方向（hello 声明**接受哪些命令**）+ **argv 三分**重建 + §26 死循环护栏同步扩 | 依赖 U6b-1 的信封已定 |
| **U6b-3** | **`--resolve` 吸收**进流通道（线上形状逐字不变，aterm 契约 2026-07-18 冻结）+ F90 不透明稳定键 | 依赖前两件；是第一条**真业务命令**，用来验证骨架 |

不改任何出方向帧的线上字节 · 不碰 monitor 侧的发送端实现（本件只做 daemon 侧 + 协议文档 + 机检；
monitor 侧发送在 U6b-3 随第一条真命令一起接）。

## 设计：入方向信封

```
→ {"id":"<opaque>","cmd":"<name>","args":{...}}      请求（一行一个）
← {"kind":"reply","id":"<opaque>","ok":true,...}     成功
← {"kind":"reply","id":"<opaque>","ok":false,"code":"...","message":"..."}
← {"kind":"cancelled","id":"<opaque>"}               取消已生效
→ {"id":"<opaque>","cmd":"cancel","args":{"target":"<id>"}}
```

四条**刻意的**选择，每条都有理由：

1. **`id` 是不透明字符串，daemon 不解析它、只回显。** 谁生成谁负责唯一 —— 客户端。
   daemon 若自己发号，重连后号段会撞（F90 的同一条道理：**不许拿会变的东西当持久键**）。
2. **应答复用出方向的 `kind` tag 空间**（`reply` / `cancelled` 是新 kind）。
   不另开一条流：旧 monitor 见到未知 kind 会**忽略**（`§10` 已有的 additive 规律），
   所以新 daemon × 旧 monitor 天然安全。
3. **取消是一条普通命令，不是带外信号。** 带外需要第二条通道或转义序列，两者都要新的解析纪律；
   而取消本身可以排队等待也没关系（它只在长命令上有意义）。
4. **错误形状对齐 `--resolve` 已有的 `{code,message}`**（协议 v1 §3 已冻结的那套），
   不发明第二种错误 JSON。

### 入方向的信任边界（这是本件的高风险点）

出方向 daemon 是**唯一写者**；入方向 daemon 变成**读取不可信输入**的一方。三条硬约束：

| 约束 | 判据 |
|---|---|
| **单行长度上限** | 超过即整行丢弃 + 回 `reply{ok:false,code:"line_too_long"}`，**不缓冲、不 OOM**。`resolve_query.rs` 已经有 stdin 上限的先例（审计 security-重要②），沿用同一个数量级 |
| **未见 Hello 之前不许有 stdin** | 机检①。理由见下 |
| **解析失败不许拖垮流** | 坏行 → 回错误 → **继续读下一行**，绝不 `panic!` / 不结束进程 |

### 为什么「Hello 之前不许有 stdin」要做成机检

Hello 是握手，客户端**必须先读到它**才知道对面是什么版本、有什么能力。
如果客户端抢在 Hello 之前写命令：

- 对**老 daemon**（不读 stdin）那些字节留在管道里，老 daemon 退出时可能 `SIGPIPE` 客户端；
- 对**新 daemon**，命令会在能力协商之前被执行 —— 而 U6b-2 正要把「接受哪些命令」放进 Hello。

这是**时序约束**，和 U6a 抓到的 PS 握手顺序**同一族**：两边单看都合理，只有合起来看才错。
U6a 的教训是这类约束光写注释不管用，必须机检。

### 为什么「命令处理器不许跑在流线程上」要做成机检

抄 `run_tmux_ls` 头注已有的纪律。流线程一旦被一条慢命令占住，**所有会话的实时行都停**——
而症状会表现为「远端会话卡住」，几乎不可能归因到某条命令上。

## 逐条实现步骤

1. `wire.rs`：加 `Reply` / `Cancelled` 两个出方向 kind；加入方向的 `Request` 类型（**只 `Deserialize`**）。
   *验证*：U6a 的 `every_wire_field_appears_in_the_protocol_doc` 会立刻红 ⇒ 逼我同步文档（这是设计意图）。
2. 新建 `src/inbound.rs`（**顶层，与 `wire.rs` 平级**）：行读取 + 信封解析 + 上限 + 命令表。

   **归属已定，不边写边定**：§1.1 的第二条线是 `observe/`（读）vs `control/`（做）。
   入方向有两层，**分开归**：
   - **传输层**（读行 / 解析信封 / 长度上限 / 回显 `id`）**不属于任何一边** —— 它跟 `wire.rs`
     是同一类东西（协议管道），所以放顶层。把它塞进 `control/` 会让「control = 做事」这条线变浑。
   - **每条命令的处理器**属于 `control/`（它们就是「做」）。`inbound.rs` 只持有命令表、
     调 `control::` 里的函数。
   
   ⇒ 依赖方向是 `inbound → control`，与既有的 `observe → control`（单向、白名单）同向，
   `layering_guard` 的现有判据不需要放宽。
   *验证*：`layering_guard` 不红；且 `inbound.rs` 里**不许出现任何 `observe::`**（读面的事不归它）。
3. 流模式主循环加 stdin reader task，`tokio::select!` 里与 writer 并列。
   *验证*：DoD ⑦ 字节对拍。
4. 机检① `hello_before_stdin_guard`：Hello 的 flush 必须在 stdin reader spawn **之前**。
   取法照 U6a 的 `ps_template_sets_the_window_title_before_writing_the_await_file`（比较字节位置）。
5. 机检② `handlers_off_stream_thread_guard`：`dispatch.rs` 里每个处理器必须经 `spawn_blocking` / `spawn`。
   *验证*：变异一个 ⇒ 红。
6. 文档 + 全量门禁。

## 实现期与计划的偏离

### ★ 护栏在本轮**当场失效了一次**，而且是我自己给它写的弱点

U6a 的 `every_wire_field_appears_in_the_protocol_doc` 头注里如实登记过两条弱点。
U6b-1 加入方向的第一步，**两条同时被命中**：

| 弱点（U6a 已登记） | U6b-1 怎么命中的 |
|---|---|
| 「只查**出现**」——常见词恰好出现就算过 | 新加的 `Reply { id, ok, code, message }` **一条都没写进文档**，护栏**全绿**。`ok` / `id` 这种词在 570 行中文文档里必然出现过 |
| （未登记）只扫 `derive(..., Serialize)` | 入方向的 `Request` 是 **`Deserialize`-only**，它的 `cmd` / `args` **根本不被扫** |

两处都收紧了：

- **判据**：从「字面量在全文任何地方出现过」改成「作为标识符出现在某个**反引号代码跨度之内**」。
  中间试过更严的「自成一个跨度」（`` `ok` ``），**误报了 3 个既有字段**——
  文档里有 `v, build_id, host_arch, …` 这种逗号连写在同一跨度的写法。⇒ 取跨度内容按标识符切词。
- **抽取面**：`Serialize` **或** `Deserialize`。出方向漏字段和入方向漏字段对下游是同一件事。

收紧后立刻抓到 `cmd` / `ok` 两个真漏 —— 逼我把入方向那节写完文档才放行。**这正是它该干的事。**

### 三处摸底与计划叙述不同（已在 Phase B 表里，此处只记结论）

「双向」的起点不是零（`--resolve` 已在读 stdin）· 载体现成没人用（`ChannelStream` 双工、
`ssh_source.rs` 零 `stdin`）· argv 是二分不是三分。

### 计划外多做的一件：应答走独立通道

计划只写「入方向背压」。实现时发现**不能与出方向共用那条 10 000 容量的通道**：
出方向丢一帧是可恢复的（`overflow` 告诉你丢了多少，行还在远端 jsonl 里），
**丢一条应答会让客户端永远等下去**。而且实时行的洪峰会把应答挤掉。

⇒ 独立小通道（256）+ writer 用 `biased` select **优先应答**。
应答通道满时**阻塞入方向而不丢弃** —— 满 = 客户端连应答都读不过来，这时候把背压顶回去正是想要的。

### 一个自找的坑：`cancel` 必须是 `MAY_RUN_INLINE` 的唯一例外

机检②要求所有处理器都 `spawn`。但 `cancel` **必须**就地跑：它就是用来打断别的命令的，
自己再排到那些命令后面去就永远不会生效。所以白名单不是妥协，是正确性要求 ——
护栏里写了这条理由，且要求任何新增白名单项**必须写明为什么它必须就地跑**。

### 测试写法上纠正了自己一次

`ping_replies_ok` 第一版用 `try_recv()` 收应答 —— 但处理器跑在**独立 task** 上
（那正是本模块的纪律），`try_recv` 会在它还没跑完时读到空。我当时补了个
「空了就重跑一次」的凑合法，那种测试**可能因为错误的原因通过**。
改成 `recv().await` 直到 `None`（sender 只有 reader task 与它 spawn 的处理器两处，
都结束后自然收尾）—— 确定性、不需要 sleep，顺便把断言改成**逐字节等值**。

### 出方向字节对拍：我在同一次验收里连打了三次假绿

DoD ⑦ 要对拍「出方向逐字不变」。前两次都得到 **0 字节 vs 0 字节**，而我照样打了
「★ 逐字节相同」：

1. 第一次 `daemon | sed` 管道把输出吞了（`timeout` 杀进程时的信号/缓冲交互）；
2. 第二次换成 `| python` 一样吞；我写了 `test -s A && test -s B && echo 非空`，
   **它失败时只是静默跳过，后面的成功消息照打**。

第三次改成**先落盘再归一**，并把「两边非空」做成 python 里的 `sys.exit` 硬前置。
真实结果：两边各 **2 帧**（`hello` + `tmux_sessions`）逐字相同，只归一 `build_id`
与 tmux 实况 `raw`（那两个逐次必然不同）。

⇒ **纪律**：对拍脚本里「非空」必须是**会让整条命令失败**的前置，不能是一个 `&&` 链上的 echo。
这是本会话第三次栽在「用 `&&`/`||` 拼出来的假绿」上（前两次：`echo "fmt ok"` 无条件打、
`grep` 的退出码被当成 `cargo` 的）。

### 阻塞（全部已修 + 各有回归测试/探针）

| # | 问题 | 实测证据 | 修法 |
|---|---|---|---|
| **B1** | **SIGTERM 回归**（我引入的）。`tokio::io::stdin()` 走**阻塞线程池**，`abort()` 停不了它，而 runtime drop 会等它 ⇒ **stdin 开着时 daemon 收到 SIGTERM 不再退出** | FIFO 接 stdin 保持开着（= monitor SSH exec 的生产形状）：HEAD **3/3 挂死 5s+**，stderr 末行已打「shutdown signal received」；父提交 100ms 退出 | `main` 末尾 `std::process::exit(0)`。流模式无待落盘状态（唯一写盘入口在一次性查询模式，早就 exit 了），stdout 每帧即 flush |
| **B2** | **1 MiB 上限在整行已进内存之后才判** —— 「不缓冲、不 OOM」是假的。`split(b'\n')` 是无界 `read_until` | 喂 512 MiB 无换行 ⇒ **RSS 6 MiB → 518 MiB**，而它照样回一条 `line_too_long`「看起来对」 | 改 `fill_buf`/`consume` 手搓：超限后**只找换行、不再塞字节** |
| **B3** | `spawn_handler` **先 spawn 后 insert**，multi_thread 下 task 可在 insert 前跑完自己的 remove ⇒ 空壳句柄永久留表 | 20 000 条命令全部回完应答后**还剩 1964 个**；且空壳让 `cancel` **撒谎**（对早就成功的命令回 `cancelled`） | oneshot 闸门：task 起来但不许开跑，直到句柄登记落地 |
| **B4** | **重复 `id` 静默覆盖** ⇒ 前一条永远取消不掉（再发 cancel 照样 `ok:true`，被「幂等」那条规则盖住）；先跑完的那条还会摘走另一条的句柄 | 实测「第一条被取消? 0 / 第二条被取消? 1」 | 明确拒绝，回 `duplicate_id` |

**B1 的教训**：`--resolve` 用的是 `stdin().take(MAX)`（真·先取上限再读），我**抄了常数没抄机制**，
还在 DoD ④ 里写下「内存不涨」——那句当时**没有任何测试**。

## 工程审计结果（E）

### 这一轮 D 审计改变了我对「护栏」这件事的判断

前面几轮的模式是「加护栏 → 用变异证明它有效 → 收工」。U6b-1 的 D 审计把这个模式的**上限**测出来了：

  **rustfmt 自己的输出**（derive 折行）和**一行沿革注释**。
- 原因是同一个：**我的变异是照着自己的实现设计的**。我知道判据是「`#[derive(` 开头那行有没有 Serialize」，
  所以我的变异去改 `Serialize`；而绕过它只需要**让那行不再是 `#[derive(` 开头**。

这条要写进主计划的横切约定：**高风险档的护栏，D 审计必须包含一个「设法绕过」的对抗视角**，
