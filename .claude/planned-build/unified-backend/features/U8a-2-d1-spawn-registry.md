## 为什么本轮不是直接写那条命令

Phase B 一查就撞上门：**主计划 §5 唯一待拍板的 D1，问的正好是 U8a-2 要做的事** ——

> **D1**「间接写」算不算违反 §41.6？daemon 一旦起 `ccm`/`claude`，**用户既有数据一定会被改**。
> 机器护栏放行（它只认 fs 写模式），**散文铁律的字面意思不放行，CI 永远不会红**。
> ① 铁律收窄为「daemon **进程自身**不许写用户既有数据」…… ② 铁律维持字面，则
> **`control/` 起 agent 这件事本身违规，本区不成立**。推荐 **①**，且**必须同时**……

⇒ 不先裁决就写命令，等于**从一条自己知道违规的路上绕过去**。

## 裁决：取 ①，理由不是「推荐里写了」

- 选项 ② 的后果是「**本区不成立**」—— 与用户 2026-08-01 的定调「**把所有控制交给 daemon**」直接冲突。
  在用户已经给了方向的前提下，② 不是一个真实可选项。
- 所以本轮**按 ① 裁决并落实它的强制条件**，而不是停下来问一个答案已由既有决定框定的问题。
  **但这是一次铁律边界变更，必须显式说明，不能埋在实现里** —— 故单独成件、单独 commit。

## 强制条件：「逐条列举」必须是机检，不是散文

D1 的推荐带一个硬条件：把起进程的写面**逐条列举**、预信任单列为受管例外。
**只在散文里列一遍不行** —— 那正是 §0.2 批评的「护栏与散文说的不是一件事」。

⇒ 交付 `readonly_guard::spawn_registry`：生产段每一处 `Command::new` 都必须在清单里，
并写明「做什么、为什么不违反收窄后的铁律」。

### 实测：生产段今天有 **3 处**起进程

| 文件 | 起什么 | 做什么 |
|---|---|---|
| `control/tmux_hook.rs` | `tmux` | 装 hook（`set-hook -g`）。改的是 **tmux server 运行期状态**，不是用户既有数据 |
| `observe/watcher.rs` ×2 | `sh` | `command -v tmux && tmux ls`。**只读**；用 `sh -c` 是为了让 `command -v` 解析 PATH |

⚠ **这个数字我数错过一次**：第一版扫描按**第一个** `#[cfg(test)]` 截断文件，
而 `observe/watcher.rs` 前部就有内联测试模块 ⇒ 它后面的两处 `sh` 全被吃掉，只报出 1 处。
又是「抽取面画小了」（本工作区第四次）。改成按 `#[cfg(test)] mod` 块**逐块配平**排除，才得到 3 处。
