# U8a-2（实现半）· 摸底结论：**先接发送端，再写命令**

- 工作区：unified-backend · 第六梯队 · 任务 #96
- 本件产出：**两个决定性实测**，把 U8a-2 的实现顺序改了

## 发现一：入方向**没有发送端** ⇒ 现在加命令等于加一条没人能调的命令

`ssh_source.rs` 里写半边的**唯一**用法是 `reader.get_mut().shutdown()`
（关掉写端让 daemon 见 EOF 自退），**零数据字节**。
（`AsyncWriteExt` 确实被 import 了 —— 就是给这个 `shutdown` 用的。差点据此推翻自己上一轮的断言，
逐个 `write_all` 查过之后确认：**那句「一个字节都没往 stdin 写过」成立**。）

实测确认：全仓**没有任何地方在构造入方向请求**（`{"id":…,"cmd":…}`）。

⇒ **U6b-1/2/3 建起来的入方向通道，今天在生产里是不可达的。**
这不是缺陷（骨架先行是刻意的），但它决定了顺序：
**现在往 daemon 加 `launch` 命令，是在一条没人能调的通道上再加一条没人能调的命令。**

⚠ **对我自己上一轮说法的精确化**：U6b-3 的报告里我把 `resolve` 称作「第一条**真业务命令**」——
那句准确（它确实是第一条有业务语义的命令、代码是真的），但读者可能推断它已在线上被调用。
**实际不是**：流式那条今天没有调用方；一次性 `--resolve` exec 也没有 monitor 侧调用方，
它是给**仓外 aterm** 的（其头注写明 aterm 现走 β TailTransport、暂不消费）。

## 发现二：daemon 侧的「第三层安全防线」**防不住任何新东西**

设计要点问「daemon 侧要不要第三层校验」。先量既有两层：

| 层 | 判据 |
|---|---|
| 前端 | sid 白名单 · launcher denylist · POSIX 引号 |
| `launch.rs` | 非空 · 长度上限 · **无控制字符**；`build_remote_ssh_ps_command` 再加「禁双引号」（**PowerShell 专属** —— native 传参畸变面）+ user/host 字符集 |

**结论：daemon 侧不该假装有一条安全边界。** 理由是结构性的 ——
入方向命令来自**已经握着这台机器 SSH 会话**的对端，它本来就能在那台机器上跑任意命令。
daemon 再校验一遍，挡不住任何它原本挡不住的东西。**那会是安全剧场。**

daemon 侧真正该做的是**形状校验**（fail-fast + 可诊断）：
参数缺失/类型不对/长度离谱 ⇒ 回一条结构化错误，而不是把畸形串塞给 shell 让它以奇怪的方式失败。
**这两者的区别要写在代码里**，否则下一个人会以为那层是安全防线而放松上游。

顺带一条：`launch.rs` 的「禁双引号」是 **PowerShell 专属**约束。命令若改走入方向通道，
**那条约束不成立也不该照抄** —— 它防的是 wt.exe/PowerShell 的传参畸变，与 daemon 无关。

## 因此：U8a-2 的实现顺序改为

| 步 | 内容 | 为什么在前 |
|---|---|---|
| **U8a-2a** | **接上 monitor 侧发送端**（往 `ChannelStream` 写请求行 + 把 `reply`/`cancelled` 从「认识但不消费」改成真消费） | 没有它，任何入方向命令都不可达；且它能让**已经写好的** `ping`/`cancel`/`resolve` 第一次真正跑起来（现成的验收载体） |
| **U8a-2b** | `launch` 命令本体（含 `send-into`） | 门（D1）已开、载体（发送端）就位之后再写 |
| U8b–U8d | 原样 | |

## 本件不改任何生产代码

纯测量与顺序订正。**没有为了「本轮有产出」而去写那条不可达的命令。**
