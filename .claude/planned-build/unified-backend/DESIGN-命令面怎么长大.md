# 设计稿 A · 命令面怎么长大（入方向命令面的可扩展形状）

- 产出：2026-08-02。用户中途点名：「daemon 的架构要仔细全面考虑，比如 usage 这种命令也可以集成进去。」
- 性质：专职设计 agent 的只读摸底 + 形状建议；**主线程逐条复核并标注处置**（见 §7）
- ⚠ 它写于 U8a-2b 实现**中途**，所以有几条「今天在漏」在本轮当场就修掉了

## §0 一句话

命令面今天有 **9 个触点、4 条护栏**，加一条命令的名义成本不高；真正的成本藏在**没有护栏的那几个触点**里。
建议在 U10 把命令数从 4 推到 8-9 条**之前**做一次小而准的注册表收口 —— 目标不是少写几行，
而是把三条今天靠约定的东西变成不可表示。

## §1 加一条命令要动几处（实测，`launch` 这一轮）

| # | 触点 | 钉它的护栏 | 漏了会怎样 |
|---|---|---|---|
| 1 | `inbound.rs::COMMANDS` | `hello_commands_match_the_dispatch_table` | 声明↔分派漂移 |
| 2 | `dispatch` 分派臂 | 同上（扫分派臂文本） | 同上 |
| 3 | 处理器实现 `control/*.rs` | `layering_guard`（只管方向，不管有没有） | — |
| 4 | 命令名进 `IPC-PROTOCOL.md` §10 | `every_inbound_command_appears_in_the_protocol_doc` | 客户端照文档发、daemon 不认 |
| 5 | **命令 `args`/`data` 的字段名进文档** | **无** | 下游只能读 Rust 源码 |
| 6 | e2e 命令名清单 | `the_e2e_command_list_matches_the_daemon_command_table` | 新命令在唯一跑真进程那层漏测 |
| 7 | e2e 新断言 + CI 地板两处 | G-A 覆盖面地板只保「套件在、地板值对得上」 | 新命令 e2e 零覆盖而全绿 |
| 8 | 起进程 ⇒ `readonly_guard::spawn_registry` | `every_process_spawn_in_production_is_registered` | **本轮实测在漏**（见 P1） |
| 9 | 含 `"--` 字面量 ⇒ `DISPATCH_FILES` | `dispatch_registry_is_complete`（**有**反查） | — |

外加两处无机检的：账本 S16 一行；monitor 侧 typed 包装。

## §2 问题（每条带证据）

- **P1 · `spawn_registry` 的扫描面是手写名单、没有反查** ⇒ `control/launch.rs` 起 `tmux` 落在盲区，
  DoD「新增起进程点必须登记」不落地也不会红。同文件上方的 `readonly_guard::scan` 早就因为
  同样的理由改成递归了，只有这一处退回手写名单。**本轮已修**（递归遍历 + 文件数自检 + 变异复验）。
- **P2 · 命令的 `args`/`data` 完全没有文档对拍。** `every_wire_field_appears_in_the_protocol_doc`
  只读 `wire.rs`；`launch` 两端都不在 `wire.rs`（请求侧手搓 `Value` 取字段，响应侧 `json!`）
  ⇒ 8 个字段一个都不在护栏视野内。**帧的字段有对拍，命令的载荷没有** —— 而后者才是新命令真正的契约面。
- **P3 · 命令名的文档对拍能被同名字段白嫖。** 判据是「§10 里某个反引号跨度切出的完整词」，
  而 §10 的帧字段表里本来就有 `status`/`path`/`name`/`sid` ⇒ 一条叫 `status` 的命令零文档直接通过。
  **本轮已修 + 已实证**：退回旧作用域 + 加一条 `status` 命令 ⇒ 旧判据**真的绿**；收到「入方向」小节后**红**。
- **P4 · `cancel` 对同步处理器无效，而 `launch` 就是同步的。** `abort()` 只在 await 点生效
  ⇒ 客户端收到 `Cancelled`，而远端 tmux 会话照样建出来、载荷照样键入。**控制面在骗调用方。**
  **本轮已修**：登记表记 `cancellable`，不可取消的回 `not_cancellable`。
- **P5 · `Disposition` 不区分「异步可取消」与「阻塞不可取消」。** `main` 是裸 `#[tokio::main]`
  （worker 数 = 可用并行度），单核机器（Pi 那一档，正是目标机型）上一条在跑的 `launch`
  就占住唯一的 worker，而 `writer_task`（出方向唯一出口）与入方向 reader 都在同一 runtime 上
  ⇒ 症状是「远端还活着但一句话不说」，且观测 watcher 在 `std::thread` 上不受影响，看起来更像网络问题。
  **本轮已修**：新增 `Disposition::SpawnBlocking` → `spawn_blocking`，并加了**接缝判据**
  （按 `dispatch` 返回的变体判，不是扫文本）。
- **P6 · 错误码两层混用，`bad_request` 一词两义**（协议级「信封 JSON 坏了」vs 命令级「参数不合适」）。
  **本轮部分修**：`launch` 的形状错误改叫 `invalid_args`；`resolve` 那条**刻意不动**
  （与仓外 aterm 的一次性契约冻结在 2026-07-18，两条路复用同一纯函数）。
- **P7 · `protocol_doc_guard` 头注宣称的强度与实现不符**：头注两处写「必须落进 §10 的两张表之一 ——
  不是『全文出现过就行』」，实现却是 `DOC.contains()` 全文子串。**本轮已修**（收到 §10 的代码跨度 + 订正头注）。
- **P8 · e2e 断言数地板不随命令数增长。** 命令名清单对拍只管名字，不管有没有为新命令写往返断言。
- **P9 · monitor 侧读行无上限**，与 daemon 入方向的 1 MiB 上限不对称。今天安全（出方向帧大小天然有界），
  但 `Reply.data` 是第一个大小由**用户数据量**决定的字段。
- **P10 · 命令面今天在生产里几乎不可达**（唯一调用点是「测试连接」那条 `ping`）。
  含义：现在改命令面的形状**没有任何生产消费方要迁**，是最便宜的一刻。

## §3 推荐形状（**不主张现在做**，见反对意见）

**R1 · `Command` trait + 注册表**，只收四样：名字 / 载荷类型 / 处理器 / 文档锚点。
配 `Disposition::SpawnBlocking`（本轮已单独落地）+ 非 async 的 `dispatch` 保持不变。
净账：文本扫描型护栏 −1（`hello_commands_match_the_dispatch_table` 整条可删，漂移不可表示），
数据对数据的护栏 +1，新增护栏 +2。

**R2 · 上线类型住进 `src/wire/` 目录**，文档对拍的扫描面从「一个文件」变成「一棵树」；
反向判据用零命中型：`control/`/`observe/` 生产段不许出现 `derive(Serialize/Deserialize)`，
白名单恰好一条（`resolve_query.rs`，理由 = aterm 冻结契约）。

**R3 · 文档对拍从「§10 全节」收到「命令自己那一小节」**（闭掉 P2 + P3 的剩余部分）。

**R4 · 错误码分两层 + 零命中护栏**（协议级 code 字面量在 `control/` 生产段零命中）。

### 反对意见（本节必须读完再决定）

1. **最强的一条：今天的成本没有被实测证明是痛点。** 4 条命令、9 个触点，其中 4 个有护栏会当场红。
   引入 trait + 注册表是**先付**结构成本去省**还没发生**的重复。本仓有反例（U6b-3 的两条机检被普通重构击穿，
   教训是「别为了整齐加抽象」）。⇒ **不主张为 4 条命令做**；主张在 U10 把命令推到 8-9 条**之前**做，
   且只做把漂移往「不可表示」推的那部分。**U10 若被推迟或砍掉，这件事一起推迟。**
2. `DOC_ANCHOR` 是约定不是事实 —— 但这不是新增局限，是把既有局限局部化，强度只升不降。
3. 改 `COMMANDS` 的形状会打断 monitor 侧的文本抽取 ⇒ 所以**保留 `pub const COMMANDS` 字面量**作镜子。
4. `Disposition` 加第四档让「取消」语义分叉 —— **语义今天已经分叉了，只是在说谎**（P4 实测）。
5. R2 第一天就要开例外（`resolve_query` 的 4 个类型 18 个字段，`rename_all = "camelCase"`）。
6. `spawn_blocking` 的活是**真的完全不可取消** —— R1 不是「修好了取消」，是「停止假装能取消」。

## §4 三个点名问题的判断

### Q2 · 一次性子命令要不要收编？判据五条

**T1 载体可达**（调用方手里有没有那条长连接）· **T2 响应有界且小**（且大小与用户数据量无关）·
**T3 处理器不阻塞**（或已落 `SpawnBlocking`）· **T4 契约不冻** · **T5（加分）频率**。

| 子命令 | 判断 | 理由 |
|---|---|---|
| `--tmux-notify` | **不收（永不）** | T1 出局：调用方是**远端机器上的 tmux hook 子进程**，手里没有 monitor 的 SSH 流 |
| `--resolve` | 已收，**保持并存** | aterm 契约冻结；两条路复用同一纯函数。⚠ 两条路今天**都零调用方**，「已收编」目前是纸面的 |
| `--fork-session` | **缓到 U11** | T4 未过（branch-anywhere 只剩发版，「U11 之前先对账」）；且它是唯一写盘入口，威胁模型要重写 |
| `--usage` / `--search` | **不收** | T2+T3 双失；`--search` 的 T5 更差（交互式延迟敏感，一次全库扫描会通过 worker 饥饿堵住实时行）|
| `--list-*` / `--read-session*` | **永不收，写进文档** | T2 硬失（`--read-session` 原样透传整个 jsonl）。收编等于亲手撤销 `--tail-only` + 旁路快照那套设计 |
| 账号四条 | **缓（U7e/U8d）** | 四条判据全过，是最像真 RPC 的一族；但 §1.5 定了 U7e 排在 U8 之后，且 `--account-trust*` 跑在换号重启链路上 |

**一句话的线**：命令面是**控制面的传输**。读面已经有它自己的两条传输（出方向推帧 + 一次性快照连接）。
把读面的批量查询搬到入方向，是在重打一场架构已经打完的仗。

**「什么时候值得付 id / 取消 / 背压这三笔」**：`id` 已经付过了（零边际成本）；
**取消收编后反而变弱**（一次性 exec 的取消是杀进程、彻底，入方向对阻塞处理器根本不生效）——
这条反直觉，要写进文档；背压 = **合并故障域**，只有命令又小又快、调用点本来就在长连接上时才值得。

### Q3 · `usage` 具体怎么做 —— **不做成入方向命令**

- **(A) 维持一次性 `--usage`** —— U10 之前的默认。
- **(B) 收编为入方向 `usage` 一问一答 —— 否。** T2 失（单帧承载全量聚合，而 monitor 侧读行无上限）、
  T3 失（同步全库扫描占 worker）、取消无效（用户关掉面板远端照样扫完）。
  收益只有「省一条 SSH exec」，而用量面板是**用户手动开一次**（无 `setInterval`），省的那点在 30s 超时预算里可忽略。
- **(C) 增量推流 `usage_delta` 出方向帧 —— 登记为「以后」。** 与零定时器铁律**不冲突**（触发源是 inotify 文件事件）；
  但**不许在 daemon 侧节流/去抖**（照抄 `TurnEnd` 的分工：daemon raw-per-record，客户端 rolling-latest + debounce）。
  **必须先解决**：出方向通道是**有损**的（`Overflow`）。丢一条 `line` 可恢复；**丢一条累加量 = 静默错数**。
  解法：delta 帧带 `byte_offset`（`line` 帧已有），offset 不连续就退回一次全量 —— 这正是选长连接双向的那条理由：**陈旧可判定**。
- **(D) monitor 自己从已收到的 `line` 帧算增量 —— 推荐，零协议改动。** `usage-core::accumulate(lines, &mut seen_requests)`
  的签名里那个共享的 `seen_requests` 正说明它是为增量组合设计的。
  ⚠ **未验证**：`--tail-only` 下历史行走快照连接、实时行走流，两条路要喂进**同一个** `seen_requests` 才不会重复计 —— 汇合点没核到。

### Q4 · 版本兼容

四条能力轴（`hello.v` / `capabilities` / `emits` / `commands`）今天在**两个方向上都安全**
（新 daemon × 旧 monitor：忽略未知 kind；旧 daemon × 新 monitor：`commands` 缺 ⇒ 空集 ⇒ 一个字节都不发）。

三个缺口：
1. **协商粒度是「名字」，契约粒度是「形状」** —— `hello.commands` 说不出它认不认识 `mode:"send-into"`。
   建议**不给命令名编版本号**，改走与出方向帧同一条纪律：`args` 只许**加**、加的必须 `serde(default)`、**语义要改就换命令名**。
2. **没有「应答侧帧 kind」这条轴。** 今天安全只因每条命令恰好回一帧。一旦有多帧应答（分块/进度/流式），
   「旧 monitor 忽略未知 kind」就从优雅降级变成**每次静默挂到超时**。
   ⇒ 任何多帧应答**必须**由独立能力 token 门控，绝不能只靠 `commands` 里有那个名字。
3. 错误码没分层（P6）。

## §6 不做什么

不从代码生成 §10 文档（它是给仓外读的冻结契约，生成物会丢掉真正起作用的「为什么」散文）·
不引入 JSON Schema / 参数 DSL（要加依赖，违反 S20 家族约束）· 不收编读面批量查询 ·
不给命令名编版本号 · 本轮不做多帧/流式应答（要先落「应答侧帧 kind 协商」+ monitor 侧行长上限）·
不在 daemon 侧加任何节流/去抖/超时 · 不让处理器自己检查取消标志（那会把取消从传输层的一件事
变成每条命令各写一遍，且没有判据保证新命令记得写）· 不为整齐删掉一次性 `--resolve`。
