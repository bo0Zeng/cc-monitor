## §1 本轮做了什么

### E56「还差什么、点哪里补齐」（已完成）

与「改动足迹」是**一体两面**：那页答「我在你机器上装过 / 写过什么」，这块答「还差什么」。
落在**机器页顶部** —— 那是落地页，新用户打开设置第一眼就在这里。

`src/settings/readiness.ts`（纯函数）+ 机器页顶部一块清单：

- **只读 S3 的账本，不发任何请求**（§1-2）。有测试直接比对「2 台 vs 1 台的 IPC 调用清单
  逐字相同」——一个「新用户装好就打开设置」的场景里，绝不能因为这块就把 N 台机器探一遍。
- **「缺」与「不知道」严格分开**，这是本模块最容易做错的地方：
  - `missing` = 测过、确认没有（账本 `fail`）。
  - `unknown` = 从没测过（账本里压根没这一格）。
  说它「缺」就是替用户下一个他没做过的结论 —— **一个刚装好什么都没点过的人会看到一屏红叉**。
  文案、`data-kind`、颜色三处都分开；摘要也分开说（「N 项确认缺，M 项还没测过」）。
- **不适用 ≠ 缺**：本机不需要 daemon（§2.4 逐字写着）；daemonless 的机器不需要 daemon
  （那是用户显式选的降级）。两条各有变异见红。
- **每条都写后果**（「没有数据源，这台机器的会话不会出现在 tab 里」），不只丢一个 ✗ ——
  让用户自己判断值不值得补。后果与轻重写在**一处**（`FACET_MEANING`），不散到 UI 里各说各话。
- 全绿时**整块不渲染**：老用户不该天天看见一个空清单。

### 本机特化扫描（上一轮，991559f）

结论如实记：**生产代码里没有功能性的本机硬编码**，命中的绝大多数在 `#[cfg(test)]` 夹具里
（那是对的）。真实残留四处已改（三处 UI 占位符写死 `pi`、一处注释里作者本机真实路径）。
⇒ 这条要求的**实质不在「去硬编码」而在 onboarding**，故落成上面那块清单。
