本区最大一块。**拆成两个 commit**：先接线（S4a），后搬 UI（S4b）。

## §0 要治的病（主计划 §5-4 逐字记录）

> `accounts` / `mcp` / `cc-bus` / `cc-bus-hooks` **各自维护 `this.origin`，`events.ts` 无任何
> origin 广播** ⇒ 四份不同步。

复核属实，且四份的**形状还各不相同**：

| 分节 | 选择器形态 | 状态字段 |
|---|---|---|
| accounts | `<select>` | `origin: string \| null` |
| mcp | 一排按钮（tab 式） | `origin: string \| null` |
| cc-bus | `<select>` | 读 `originSel.value` |
| cc-bus-hooks | `<select>` | 读 `originSel.value` |

用户在「账号」里切到 aya，转头看「MCP」还停在上一台 —— 而这两块讲的都是**同一台机器**。
主计划给的最终形态是：**由「当前在哪台机器页」这个上下文取代**。

## §2 S4a 方案

```ts
// null = 本机；字符串 = 某台远端的 origin
getCurrentMachine(): string | null
setCurrentMachine(origin: string | null): void
subscribeMachine(fn: (origin: string | null) => void): () => void
```

- **不持久化**。「我现在在看哪台」是会话内的导航状态，不是配置。
  存下来会让下次打开设置停在一台可能已被删掉的机器上。
- 通知**只在值真变时**发（同值重复 set 不通知）—— 否则四个订阅者会互相激起
  一串无意义的 reload（每次 reload 都是一次 ssh 往返）。
- 订阅者用 `try/catch` 隔离：一个订阅者抛异常不能让其余三个收不到通知
  （同 `panel.ts::safeBlock` 的思路）。

四处改法一致：选择器 `change` → `setCurrentMachine(v)`；订阅 → 值变了就同步自己的
选择器显示 + reload。**reload 仍然只在值变时发生**，不新增任何轮询。

## §4 S4b-1（已完成）：每台机器一页 + 点行进详情页

S4b 太大，按 loop 授权再拆。**本轮 = S4b-1**：路由器支持动态增删与一层子项，
每台机器开一页（编辑表单搬过去），列表里只留一行（名字 + 状态 + 点进去）。

- 路由器加 `parentId`（**只支持一层子项** —— 够用，且不必去想「孙子项怎么缩进 /
  折叠状态存哪」这些本轮没有的问题）与 `removeRoute`。
  **注销当前页时会切到父页**，否则用户停在一个已被摘掉的页面上看空白。
- `RemoteSection` 收一个 `MachinePagesHost`（开页 / 收页 / 跳过去三件事）。
  **抽成接口而不是直接传 router**：分节不该知道路由器长什么样，也让它在没有路由器的
  场合照常工作 —— **不传就是老形态**，既有单测与任何不带路由器的宿主零影响。
- 状态条从卡片 legend **移到列表行**（§2.3 里状态就是列表的一列；详情页上用户看的是
  动作按钮本身的结果，不需要再来一份缓存结论）。本机行与机器行共用同一份渲染
  （`renderStatusCells`），免得两处慢慢长歪。
- 详情页上的卡片去掉折叠箭头与删除按钮（一页只有它，没有可折的必要；
  删除入口在列表行上，那里才看得见「删的是哪一台」）。

## §4bis S4b-2（已完成）：四块分节跟着当前机器页走 + 本机也有一页

**S4a 那个半截状态就此消掉**：那时三块的下拉只列远端、表示不了本机，收到 `null`
只能原地不动；现在**本机页上它们压根不出现**，「表示不了」这件事也就不存在了。

- 路由器加 `onNavigate`（切页有两个入口 —— 点导航项 / 点列表行，只有路由器这一层
  两条都覆盖得到）与 `pageContentOf`。`navigate` 同页早退，**不重复通知**
  （订阅者要做搬 DOM 这类有代价的事）。
- 本机也注册成一页（`LOCAL_MACHINE_PAGE_ID`），列表第一行点得进去 ——
  §40「本地 = 不走 ssh 的远端」不只是说法，它在导航里就该和别的机器长得一样。
- 四块 per-machine 分节收进一个 slot，按当前机器页整块搬 DOM。
  **单例 + 搬 DOM，不给每台机器各起一份**：起 N 份意味着 N 倍构造开销与 N 份互不相干
  的缓存，而同一时刻只有一台机器的页面可见。
- 每块标注 `appliesTo`（依据主计划 §2.4 那张表）：
  「账号」= 远端（本机的多账号入口是 L3a 的欠账）；
  「终端集成」= 本机（PowerShell `$PROFILE`；远端的对应物是详情页上的「装/卸 ccm」）；

### S4b-3a（已完成）：`resumeCommandRemote` per-machine 化

主计划 §5-1 记的建模缺陷：resume 命令是**全局单值**，而「装 ccm 助手」是**每台机器
一个按钮** ⇒ A 机装了 ccm、B 机没装时，数据模型根本表达不出来。于是「装完 ccm 却忘了
改 resume 命令」是个**结构性陷阱**（那两处此前还隔着两个顶层组）。

- `RemoteHostConfig` 加 `resumeCommand`；**空 = 沿用全局默认**。
  刻意**不做数据迁移** —— 迁移会静默改写用户已有的设置；回退让「没填过 = 行为一字不变」。
- `pickResumeCommand`（纯函数）+ `resolveResumeCommand`（IO 包装）。
  6 个消费点全部改为按 origin 解析 —— 它们**本来就手握 origin**，只是没拿它查值。
- UI 输入框放在「装/卸 ccm」按钮**紧邻处**，这正是 §5-1 说的那两处不该隔开。

**S1 那套编译期穷尽检查当场兑现了价值**：加字段后 `tsc` 一次性点出全部 6 个构造点
（含 3 个测试夹具），不用靠人去找。

### 复核时发现四块的病比记录的还重一档

主计划记的是「四份不同步」。实际查下来，**`cc-bus-hooks` 连 `change` 监听都没有** ——
它的下拉只在用户点「检查」时被读一次。也就是说那一块的「当前机器」从来就不是一个状态，
只是一个待读的 DOM 值。这解释了为什么四块连「怎么算切换了」都对不齐。

### 三个刻意的设计决定

1. **同值不通知**。四个订阅者收到通知就 reload，而每次 reload 是一次 ssh 往返。
   同值也广播的话，四块之间会互相激起一串无意义的往返 —— 那就是变相轮询，撞 §1-2。
   有测试直接数 `invoke` 次数。
2. **订阅者异常隔离**。一块抛异常不能让其余三块收不到通知。这里的后果比白屏更隐蔽：
   其余分节会**停在上一台机器**上，界面看不出异常，用户以为在看 aya 其实在看 nano。
3. **切换不自动发诊断**（`cc-bus-hooks`）。那一块的既有语义就是「点了才发」
   （只读诊断，不替用户改 `~/.claude/settings.json`）。跟着切换自动发就成了变相轮询。

### 一个如实登记的半截状态

`accounts` / `cc-bus` / `cc-bus-hooks` 的下拉**只列远端**，表示不了「本机」。
收到 `null` 时它们**原地不动**，不乱选一台 —— 乱选比不动更糟（用户以为在看本机，
其实在对某台远端下命令）。这是半截状态，**S4b 从根上解决**：本机那一页压根不会包含
只对远端有意义的分节。已写成测试（连同「乱选一台」的变异）。
