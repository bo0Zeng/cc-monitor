## §2 S4a 方案

```ts
// null = 本机；字符串 = 某台远端的 origin
getCurrentMachine(): string | null
setCurrentMachine(origin: string | null): void
subscribeMachine(fn: (origin: string | null) => void): () => void
```

- **不持久化**。「我现在在看哪台」是会话内的导航状态，不是配置。
  存下来会让下次打开设置停在一台可能已被删掉的机器上。
- 通知**只在值真变时**发（同值重复 set 不通知）—— 否则四个订阅者会互相激起
  一串无意义的 reload（每次 reload 都是一次 ssh 往返）。
- 订阅者用 `try/catch` 隔离：一个订阅者抛异常不能让其余三个收不到通知
  （同 `panel.ts::safeBlock` 的思路）。

四处改法一致：选择器 `change` → `setCurrentMachine(v)`；订阅 → 值变了就同步自己的
选择器显示 + reload。**reload 仍然只在值变时发生**，不新增任何轮询。

## §5 代码审计结果（Phase D，S4a）

**做法如实记**：未开并行审计 agent，主线程自审 + 变异兜底（退出码判定，不再 grep 文本）。

### 复核时发现四块的病比记录的还重一档

主计划记的是「四份不同步」。实际查下来，**`cc-bus-hooks` 连 `change` 监听都没有** ——
它的下拉只在用户点「检查」时被读一次。也就是说那一块的「当前机器」从来就不是一个状态，
只是一个待读的 DOM 值。这解释了为什么四块连「怎么算切换了」都对不齐。

### 三个刻意的设计决定

1. **同值不通知**。四个订阅者收到通知就 reload，而每次 reload 是一次 ssh 往返。
   同值也广播的话，四块之间会互相激起一串无意义的往返 —— 那就是变相轮询，撞 §1-2。
   有测试直接数 `invoke` 次数。
2. **订阅者异常隔离**。一块抛异常不能让其余三块收不到通知。这里的后果比白屏更隐蔽：
   其余分节会**停在上一台机器**上，界面看不出异常，用户以为在看 aya 其实在看 nano。
3. **切换不自动发诊断**（`cc-bus-hooks`）。那一块的既有语义就是「点了才发」
   （只读诊断，不替用户改 `~/.claude/settings.json`）。跟着切换自动发就成了变相轮询。

### 一个如实登记的半截状态

`accounts` / `cc-bus` / `cc-bus-hooks` 的下拉**只列远端**，表示不了「本机」。
收到 `null` 时它们**原地不动**，不乱选一台 —— 乱选比不动更糟（用户以为在看本机，
其实在对某台远端下命令）。这是半截状态，**S4b 从根上解决**：本机那一页压根不会包含
只对远端有意义的分节。已写成测试（连同「乱选一台」的变异）。
