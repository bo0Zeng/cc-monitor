# S3 — 机器列表页：本机是第一行 + 状态矩阵

主计划 §2.3 的「机器」落地页。

## §0 硬约束（不是建议，是主计划里已经论证过的红线）

1. **状态灯绝不引入轮询**（§1-2）。行上的状态**一律**是「上次动作的缓存 + 时间戳」，
   文案必须写「3 分钟前」，**绝不显示成实时**。
   依据：`INVARIANTS §41`（daemon 生产段零定时器，`no_timer_guard` 钉住）
   + `cc-bus-section.ts` / `config-surface-section.ts` 文件头各自写死「不新增轮询」。
2. **状态性警告绝不进 hover-only 图标**（§1-3）。依据 `INVARIANTS §12`：
   「用户看到了但没注意到关键信息」**已真实发生过一次**。

⇒ 本轮的核心不是「把状态查出来」，而是**「把已经知道的状态诚实地摆出来，连同它有多旧」**。

## §1 本轮做什么、不做什么

**做**：

1. `src/settings/machine-status.ts` —— per-origin 的**状态账本**：谁写、写什么、多旧。
   纯逻辑 + 一个 localStorage 存档，**读的时候绝不触发任何探测**。
2. 把已有的动作处理器接上账本（测试连接 / 装卸 daemon / 装卸 ccm）。
3. 每台机器的行（= 折叠时的 legend）上渲染状态条 + 相对时间。
4. **本机行**：列表第一行、不可删（§40「本地 = 不走 ssh 的远端」的诚实表达）。

**不做**（划给后续，理由写清）：

- **点行 → 详情页** → S4。本轮点行仍是就地展开今天那张 `MachineCard`。
- **工具条整合**（+添加 · 从 ssh config 导入 · 批量导入 · 端口转发 · 启用远端模式）→ S4
  一起做。这几个控件**今天都已经存在**，只是没排成一条工具条；单独重排是纯视觉改动，
  与 S4 要做的 `MachineCard` 提取会撞在同一片 DOM 上，分两次做等于改两遍。
- **主动去查状态**。账本只由**用户动作**填充；没动作过就显示「未测过」。
  这不是偷懒——主动查就是轮询的另一种说法（打开设置就发 N 台机器的 ssh 探测）。
- acct-iso / 账号数两个格子**留位不填**：它们的动作入口在 S4 要建的详情页「账号」栏里，
  本轮接上去等于先把 S4 的接线做一半。账本的字段先定义好，S4 填。

## §2 方案

### §2.1 状态账本

```ts
type Facet = "connection" | "daemon" | "ccm" | "acctIso" | "accounts";
interface FacetState { kind: "ok" | "fail" | "na"; detail?: string; at: number }
recordFacet(origin, facet, state)      // 写：由动作处理器调
readStatus(origin): MachineStatus      // 读：**同步、纯读**，绝不发起 IO
forgetMachine(origin)                  // 机器被删/改名时清
formatAge(at, now): string             // "刚刚" / "3 分钟前" / "2 小时前" / "5 天前"
```

- `kind: "na"` 是**「不适用」**，不是「不知道」：本机不需要 daemon（§2.4 表里逐字写着
  「**不需要**」，`watcher.rs` 直读 jsonl）。把「不适用」和「没测过」混成一个值，
  用户会以为本机缺了个组件。
- 存档在 localStorage（UI 缓存，不是权威数据）。**跨重启保留**是对的：
  时间戳一起显示，旧就是旧，诚实即可；清空反而让列表永远是一片「未测过」。

### §2.2 「读不触发探测」怎么钉

不是靠注释约定。测试里 **mock 掉 `ipc/commands`，渲染整个机器列表，断言零次调用**。
这条比源码扫描强：源码扫描只能证明「没 import」，证明不了「渲染时没调」。

### §2.3 本机行不进 `this.cards`

**这是 S1 的安全边界**：`RemoteSection.save()` 拿 `this.cards` 算 patch。
本机不是一条 `RemoteHostConfig`，混进去会被当成一台远端机器写进 config.json。
本轮加一条测试：**加了本机行之后，保存写出去的机器数不变**。

## §4 代码审计结果（Phase D）

**做法如实记**：同前几轮，未开并行审计 agent，主线程自审 + 变异兜底。

### ★ 变异脚手架自身出了问题，导致第一轮「全红」是假的

第一轮我用 `case "$OUT$TS" in *failed*)` 判定红绿，其中 `$TS` 是 `npm run check:types`
的输出——**它会连带跑 cargo，而 cargo 全绿时也会打印 `0 failed`** ⇒ 判据恒真 ⇒
8 条全部误报成「红 ✓」。

发现方式：⑧「SSH 不通也断言 daemon 状态」报了红，可我**根本没为它写过测试**。
数不对就查，一查就塌。改用**退出码**判定（`if npx vitest run …; then 绿 else 红`）
重跑，真实结果是 **8 条里 2 条其实没覆盖**：

- **④ 时钟回拨那条是等价变异** —— `if (d < 0)` 被紧接着的 `if (d < MIN)` 完全覆盖，
  是**死码**。已删除（并把「负数也落这一档」写进注释）。
- **⑧ 确实没测** —— 补测试时又撞出一个更隐蔽的问题（见下）。

**连带复查**：S1 那一轮的第一批 7 条变异用的是同一个坏判据。已用退出码全部重跑，
**7 条确实全红**，S1 的结论成立，无需更正。

### 补 ⑧ 的测试时撞出的问题

`onTestConnection` 在进 `try` **之前**就 `new Channel<ConnectStage>()`。jsdom 里没有 Tauri
宿主，那句会抛；而调用点是 `() => void this.onTestConnection()` ⇒ 抛出去变成一条**被吞掉的
unhandled rejection**：按钮点了什么都不发生，测试也看不出原因（我第一版就卡在这，
表现是「IPC 一次都没被调用」）。已 mock `@tauri-apps/api/core`。
**这条在生产里不是 bug**（有 Tauri 宿主），但它说明这类 handler 的失败是静默的。

### 其余判断

- **SSH 不通时不给 daemon 那格下结论**：记 `fail` 等于替用户断言「远端没装 daemon」，
  而事实可能只是网络不通，那条错结论会一直挂在列表行上。已按「不知道就不写」处理。
- **卸载成功 ≠ `ok`**：卸载 daemon/ccm 成功意味着这台机器现在**没有**那个组件，
  结论是 `fail`。所以这两处刻意不用 `runRemoteAction` 的 ledger 参数
  （它把「动作成功」映射成 `ok`，本例正好相反）。
- **「不适用」`na` 与「没测过」`undefined` 是两个值**：本机不需要 daemon，
  混成一个会让用户以为本机缺组件。
