## 0. 动手前先证成：这个抽象**现在**该建吗

本工作区自己定的纪律（STATUS）：「注册表的正当性来自**有 ≥2 个真实工具要求同一套机制**。
提前建等于为假想需求设计（unify-launch R12 踩过的同型错误）」。
unify-launch 全程我三次拒绝过提前抽象（R12 的 registry、R15 的 `passThrough`、
B02 的 `--bus-id`、B03 的 `inbox_id_from_filename`），所以这条不能靠计划里写着就算数。

**实测证据（不是引用计划表，是数真代码）**：

| 关注点 | 独立实现数 | 实证 |
|---|---|---|
| 「备份→写→**读回比对**→回滚」 | **4 处** | `profile_installer.rs:239`、`sftp.rs:660`、`sftp.rs:725`、`sftp.rs:767` |
| vendor + 指纹 + 过期检查 | **2 套不同写法** | `cc-acct-iso` 的 `.vendor_id`（6 文件指纹） vs `code-picture-core` 的 `build.rs::check_vendor_freshness`（软警告） |
| 能力自报 | **2 套不同协议** | `ccm --ccm-probe` 的 `capabilities=` 文本 vs daemon `hello` 帧 |

→ **前提成立**。而且不是"将来会有第二个"，是**现在就有四个/两套/两套**。

## 1. 抽象的**具体收益**（不止去重——去重本身不足以证成抽象）

实测发现四处「读回比对」**语义并不一致**，其中本机侧那份明显更弱：

| 处 | 比什么 | 失败时 |
|---|---|---|
| `profile_installer.rs:242`（写入） | **只比长度** `written.len() != updated.len()` | 从备份恢复 |
| `profile_installer.rs:305`（剥离） | **只比长度** | 同上 |
| `sftp.rs:729`（远端 ccm CLI） | **比内容** `cli_back != CCM_CLI_SCRIPT` | 报错，不动 profile |
| `sftp.rs:767`（远端 profile） | **比内容** | 回滚原文件 |

**本机侧只比长度 = 同长度的损坏静默放过**（字节翻转、编码变形、CRLF↔LF 等长替换）。
而 `~/.bashrc` / `$PROFILE` 写坏的后果是用户下次开终端就炸。

→ **T01 的第一个可验证收益：统一写入器把本机侧从「长度比对」升级为「内容比对」。**
这条要有一个**会红的测试**：构造一个"长度相同但内容不同"的写后状态，断言旧实现放过、
新实现拦住。**不是重构完跑一遍原有测试就算数**——原有测试挡不住这个，否则它早就红了。

## 2. DoD

- [ ] `ToolSpec` 声明五个正交关注点的最小契约：**源 / 落点 / 探测 / 装升卸 / 配置面申报**。
      每一项都必须能被现有五套工具中的**至少两套**实例化；**只有一套需要的字段不进 ToolSpec**
      （放该工具自己的扩展位）。
- [ ] 通用写入器 `verified_write`：备份 → 写 → **内容级读回比对** → 不符回滚。
      本机 fs 与远端 SFTP 两种落点各是它的一个实现，**共用同一份校验与回滚语义**。
- [ ] `profile_installer.rs` 的 PowerShell profile 路径改为调用它（**行为等价 + 校验升级**）。
- [ ] 探测统一成「结构性扫描」范式（`sftp.rs::ccm_cli_has_required_elements` 的形状）。
      **不得降级为固定 needle**——账本明写「已实证固定 needle 是空转的」。
- [ ] 配置面申报：每个工具声明它**碰哪些用户文件**，供 T02 的审计视图消费。
      本轮只产出数据，不做 UI（T02 才做）。

**不做什么**：
- **不碰 `tabs.ts`**（D5/K4：那里有 F09 的 1 阻塞 + 5 重要修复，重写极易丢）。
- **不做全局 MCP**（用户定调；`mcp-section.ts` 的 SS-14 读写分界原样保住）。
- **不改 `shared/ccm` 本体**（账本：12 条 print-parity + 39 条 ccm-cli 是外部预言机，
  动它风险最高、可观测性最低）。
- **本轮不吃新工具**（cc-bus 部署 / code-picture 搬迁是 T05/T06）。MASTERPLAN §4 第 3 点：
  先用五个**已知行为**的工具验证抽象，反过来做等于用未验证的抽象接未集成的工具、两个变量一起动。

## 3. 实现步骤

1. 把四处「读回比对」的**实际语义差异**逐条列出来（已完成，见 §1 那张表），
   定下统一后的语义 = **内容比对 + 回滚**（取四者中最强的）。
2. 写 `verified_write` 的纯逻辑部分（校验与回滚决策）+ 单测，**先证明它能拦住长度相同的损坏**。
3. 本机 fs 落点接上去，`profile_installer.rs` 改调用；跑既有 PowerShell profile 测试证明行为等价。
4. 远端 SFTP 落点接上去，`sftp.rs` 三处改调用；跑 `ccm-acceptance` 等真机套件证明等价。
5. `ToolSpec` 声明 + 五套工具各自实例化（**先只声明，不改它们的行为**）。
6. 结构性扫描抽成可复用形式，五套各自给出自己的「必备要素」清单。

## 4. 测试策略

- **长度相同的损坏**：这是本功能存在意义的直接证明，必须有会红的测试。
- **行为等价**：既有 PowerShell profile 测试 + `ccm-acceptance` / `ccm-print-parity` 真机套件
  全绿，且**不放宽任何既有断言**。
- **ToolSpec 的字段纪律**：一条测试断言"每个字段至少被两个工具实例化"——
  防止我把只有一套需要的东西塞进公共契约（这正是本工作区反复拒绝的病）。
- 变异验收：把内容比对改回长度比对 → 必红；去掉回滚 → 必红；结构性扫描换成固定 needle → 必红。
