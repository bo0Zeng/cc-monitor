## 1. ★ 开工复测抓到一件**真的漏了的事**：`BUILD_ID` 没 bump

STATUS「必须做但刻意延后的」第 1 条写死：

> **bump `BUILD_ID`**（现 `p1q-accounts`）+ 重部署 —— 排在 **P5**。
> 不 bump ⇒ 已部署的旧 daemon 不被判 stale ⇒ 不自动重装 ⇒ **P1 的修复在远端休眠**。

**P5 没做。** 复测时一 grep 就是 `const BUILD_ID: &str = "p1q-accounts";`。

这是「**有些遗漏不会红任何测试**」的又一个标本，而且是最难察觉的那型：
`BUILD_ID` 是个字符串常量，**改不改都全绿**——173 个 daemon 测试、622 个 monitor 测试、
866 个 vitest 没有一个会动。而漏掉它的后果是**整轮工作（P0-P6）在已部署的远端一行都不生效**：
旧 daemon 报同一个 id ⇒ monitor 判它不 stale ⇒ 不自动重装 ⇒ 用户那边延迟还是 16s。

⇒ P7 补上：`p1q-accounts` → **`p1r-event-liveness`**。

### 1.1 单一事实源已经在了，所以只改一处

`build.rs::emit_daemon_build_id` 从 daemon 源码里抠出 `const BUILD_ID` 的值，
emit 成编译期 env `DAEMON_BUILD_ID`，monitor 的 `EXPECTED_DAEMON_BUILD_ID` 用它。
**实测确认传导**（不是看代码推断）：

| 核实项 | 结果 |
|---|---|
| daemon 二进制里的字符串 | `p1r-event-liveness` ✓ |
| 最新那份 build script 的 `output` | `cargo:rustc-env=DAEMON_BUILD_ID=p1r-event-liveness` ✓ |
| `const BUILD_ID` 是否只有一行（`extract_build_id` 取 `find` 的第一条） | 只有一行 ✓ |
| 有没有测试钉死具体字面量 | 没有（测试用的是 `p1e`/`p1h`/`p1x` 这类假 id） |

### 1.2 顺带确认「内嵌 daemon 陈旧」不是本轮引入的问题

bump 之后 `cargo build` 冒出两条 `cargo:warning=内嵌 daemon <arch> 比 daemon 源码旧`。
**那是 `build.rs` 里专为这件事装的安全网在正常工作**，不是本轮弄坏了什么：

- `src-tauri/embedded-daemons/` **不被 git 跟踪**（发版由 `release.yml` 现场交叉编译）
- 本机那两份的 `.build_id` 是 `p1b-overflowwriter` / `p1h-bg-badge` —— **早就落后于 `p1q`**

⇒ 陈旧是本机开发态的既有状况，与 bump 无关。**真机生效仍需重部署**，这条如实写进了
`INVARIANTS §41.5` 与 §24bis。

## 2. 复测到的第二件：`§24bis` 里有三处表述已经过时

不是写错，是**被后来的功能解决了而文档没同步**（本区第十七次抓到同型）：

| 原文 | 实际 | 处置 |
|---|---|---|
| 「降到 ~10ms 是 P3/P5 的事」 | P3/P5 已交付，8s 推帧间隔**整个删了** | 补实测数字（27ms / 126ms）并指向 §41 |
| 「**P3 落地后收紧** rc=1 判据」 | **P3 已收紧**（`classify_tmux_probe`） | 划掉待办，并补上一处比原设想更细的地方（见下） |
| 「尚未真机生效…直到 P5 一并 bump」 | P5 漏做，**P7 才 bump** | 如实写「原计划排 P5、P5 漏做、P7 抓出来」 |

第二条那个「更细的地方」值得留档：收紧 rc=1 时**刻意不依赖「pidfd 是否醒过」**——
那会在 pidfd 路失效时把 rc=1 **永久**压成 `Unobservable` ⇒ **永不 retire**。
改成直接查 `/proc` 里 server pid 还在不在（一次存在性读，无挂死风险），有变异钉住。

## 3. `INVARIANTS §41`：写实际落成的样子

新增一节（**只加不改既有条款**，遵主计划账本第 5 行）：四路事件表（每格带实测延迟 +
测法）· 一条**正确性**改进（pidfd ⇒ PID 复用在机制上不存在）· 三盲区分类 ·
零定时器护栏的判据与两条派生纪律 · 兼容与部署。

三处刻意的诚实边界：

1. **同一场景两个数（18ms / 126ms）都留档**，取有对照组的 126ms 作对外数字，
   并写明「差异在测法不是行为」。铁律 3 要的就是这个：**不许把估算写成实测**。
2. **CI 那个毫秒数标明是上界**（`wait_line` 0.5s 轮询 ⇒ 粒度 500ms），**不是性能基线**。
3. **盲区②写清「今天的轮询也没在做这个」**——卡死的 CC 在 `tmux ls` 里照样在。
   不这么写，读者会以为删轮询是拿盲区换的延迟。**实际是零损失。**

顺带把 P5 那条补进 §24：死亡帧是 `remote_tx` 的**第四个**生产者，**同样只经 emitter**、零新写点；
它绕过的是 miss 计数，**不是**兜底路——`RETIRE_MISS_THRESHOLD >= 2` 与快照对账一字未动。

## 4. E34 结案（含**对它自己原措辞的三处订正**）

E34 是本区的来源项。结案时把登记时就写错的三条一并订正 —— **不是执行走样，是登记写错**：

| # | E34 原文 | 实际 |
|---|---|---|
| ① | 「**daemon 零改**」 | **不成立**，用户当日松了该红线。零改做不到正向死亡帧，16s 只能降到「新间隔×2」（`RETIRE_MISS_THRESHOLD >= 2` 是编译期断言、判据本身就是轮询式的） |

（只有它有「server 重启」这个时机），**`shared/ccm` 一字未改**。

### 4.1 E33 只解了一半，就只标一半

E33（那条「变灰慢到被当成 bug」的用户观测）有两半：**① 标定两个常量** ·
**② 给 tab 加可见诊断，让三格一眼可分**。

- ① **被更好的东西取代**：`TMUX_EMIT_INTERVAL` 整个删了，标定的必要性大幅下降
- ② **仍未做**，而且三格的内容要跟着改写（「在等那 ~16 秒」现在≈不可感知；
  「daemon 没在发帧」要多列一种成因：**hook 没装上**）

⇒ E33 标成「**延迟那半已解，诊断那半未做**」并写明后者是 UI 改动、不在本区范围。
**不整条划掉** —— 那会把一件没做的事记成做完了。
