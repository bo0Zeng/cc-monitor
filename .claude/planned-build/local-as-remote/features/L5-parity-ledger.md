## 1. 开工复测：计划里的命令数是**旧的**，而且天真的数法会数出三种不同的答案

主计划 §1 L5 写「枚举全部 **119** 个 Tauri 命令」。实测：

| 数法 | 结果 | 这个数字是什么 |
|---|---|---|
| 主计划记的 | 119 | **过时**（写下时的值） |
| `grep -c '#\[tauri::command\]'` | **127** | **错**——见下 |
| 剥掉注释后的属性行 | 121 | 接近，但仍多一个 |
| **`generate_handler!` 里的条目** | **120** | ✅ **这个才是「前端能调到的命令」** |
| 剥注释后按**函数名去重** | **120** | ✅ 与上一行**对上了** |

**对账结果：120 = 120，未登记 0 条，登记了但无属性 0 条。** 今天是干净的。

### 1.1 那 7 个差额是什么——**其中 6 个是「扫源码守卫」的经典陷阱**

`127 → 120` 拆开：

| 差额 | 数量 | 成因 |
|---|---|---|
| **散文里逐字提到 `#[tauri::command]`** | **5** | `hooks_diag.rs:501,937` · `ssh_source.rs:14,3239` · `tmux.rs:122` —— 都是在解释「这段藏在 `#[tauri::command]` 里所以单测碰不到」 |
| **文档注释制造的假阳性函数** | **1** | `history.rs:987-989`：doc 注释里写了 `#[tauri::command]`，紧接着下一行就是 `fn build_resume_ps_command` ⇒ 天真的正则把这个**私有 helper** 认成了命令 |
| **同名的平台 cfg 变体** | **1** | `bring_monitor_to_front` 在 `lib.rs` 里有两份（`#[cfg(windows)]` / 非 windows），**一个逻辑命令、两份实现** |

**★ 第二行是我自己当场踩进去的**：做这个复测时第一版正则就报了「`build_resume_ps_command`
带属性却没登记」——看起来像个真发现（漏注册 = 运行时 `command not found`、**不是编译错**，
`ssh_source.rs:3239` 的注释专门警告过这一点）。**去看定义才发现那行根本没有属性。**

⇒ **对 L5 的直接约束**（写进实现，不是写完再说）：

1. **数之前先剥注释** —— 否则光散文就多 5 个。这与 P4/P6 那七次自指陷阱**同族**：
   扫源码的守卫必须先把「代码」和「关于代码的话」分开。
2. **按函数名去重，不按属性出现次数计** —— 平台 cfg 变体是一个命令。
3. **以 `generate_handler!` 为准，而不是以属性为准** —— 属性只说「它能当命令」，
   `generate_handler!` 才说「前端真能调到」。**两者对不上本身就该是一条断言**
   （今天差 0，正好可以钉死在 0）。
4. **数完先确认数的是不是那个东西**（本区第一次应用这条，来自 `zero-poll-liveness` P5）。
