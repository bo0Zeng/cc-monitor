## 1. 计划最担心的那件事**没有发生**

主计划把 L0 列为「**唯一可能推翻整个方向**的一步」，理由是
「WebKitGTK 的发行版碎片化是 Tauri 的知名痛点；**如果 L0 很痛，那正是那个重写决策的真实数据点**」。

**实测（aya，Linux 7.0.0-28-generic）：一点都不痛。**

| 项 | 结果 |
|---|---|
| `pkg-config --exists webkit2gtk-4.1` | ✓ 已装 |
| `pkg-config --exists javascriptcoregtk-4.1` | ✓ 已装 |
| `pkg-config --exists libsoup-3.0` | ✓ 已装 |
| `npm run build`（`tsc && vite build`） | **rc=0** |
| `cargo build`（src-tauri **完整 app 二进制**，不是 `--lib`） | **rc=0** ⇒ `target/debug/monitor`（393 MB debug） |

**零系统包安装**（红线「不装软件包」全程未触碰——三个依赖本来就在）。

### 1.1 这条数据点该怎么用，写清楚

⇒ **给重写决策的如实结论：WebKitGTK 碎片化在这台机器上不构成理由。**
但**范围要写死，别外推**：这是**一台**机器、**一个**发行版的读数。
「Tauri 在 Linux 上到处都好装」不是本条能支持的结论 —— 它只能否掉
「**在我们自己的开发机上**这件事很痛」这个具体假设。真要覆盖发行版碎片化，
得跨发行版测，而那不在本区范围里。

## 2. 「起 app」这半**刻意没做**，而且理由不是谨慎，是一条具体的后果

STATUS 的 `[待定]` 里早就写了建议：「先在 aya 上只做**能构建**（`cargo build` + `npm run build`，
**不起 app**）；起 app 那步再决定，因为它会碰真实配置」。本轮照此执行。

**但本轮多出一条更硬的理由**——`zero-poll-liveness` P7 刚把 `BUILD_ID` 从
`p1q-accounts` bump 成了 **`p1r-event-liveness`**：

> 用**本分支**构建出来的 app 一旦起来并连上用户已配置的远端，
> 就会把那些机器上的 daemon 判成 **stale** ⇒ **自动重装**。

那是**对外的、会改用户真实机器**的动作，本轮没有授权。
（本机 `~/.cc-monitor/bin/` 那个正在跑的 daemon 也在红线里。）

**沙盒 HOME 能绕开这条**，但代价是在用户正在用的桌面上弹一个窗口，
收益（「窗口能画出来」）远小于打扰。⇒ **登记，不做。**

## 3. 本轮没做的（如实登记，不含糊）

| # | 事项 | 为什么 |
|---|---|---|
| 1 | **起 app**（`cargo tauri dev` / 直接跑二进制） | §2：会触发远端 daemon 自动重装；且 STATUS 原本就建议分两步 |
| 2 | **「既有远端功能在 Linux 宿主上可用」** | 它要先起 app ⇒ 随第 1 条一起挂起 |
| 3 | **产物打包**（AppImage 与否） | STATUS 里另有一条 `[待定]`（建议 AppImage 先）。**打包不是「能构建」**，是发版面的事，而红线写着不发版 |
| 4 | **跨发行版验证** | §1.1：本条读数只覆盖一台机器，不外推 |

⇒ **L0 只签收「可构建」那半**，功能表里的状态如实写成「构建 ✅ / 起 app 待授权」，
**不整条标绿**（同 `zero-poll-liveness` 对 E33 的处理：只解了一半就只标一半）。
