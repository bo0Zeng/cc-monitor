# Z07 — 版本钉 + 声明漂移检测（销 BACKLOG E37）

> 主计划：`../MASTERPLAN.md` §1 Z07 · §3 账本第 11 行 · §0.1 成功标准 8
> 前置：**Z06**（`941e13d`，`NATIVE_IDENTITY` 声明就是要绑版本、要拿去对拍的那个东西）

## 1. E37 的实质

`CLAUDE_CONFIG_DIR` **在官方 settings 页与环境变量页都查不到任何文档**，而整套多账号隔离
压在它上面。它失效时**今天没有任何东西会响**——而最坏形态不是报错，是**静默共用身份**
（以为在用 z、实际烧 b 的额度，UI 上完全看不出来）。

**本功能买到的是「快速失败」，不是「保证可迁」**（主计划 §6 R-新1 已写死这条边界）：

- **换位置**（改名 / 搬目录）⇒ 报出来，改声明 + `sync --apply` 迁过去
- **换机制**（凭据进 OS keyring）⇒ 按目录切身份**整体失效**，任何检测都救不了那件事；
  但下面的 D1b/D2 会让它**当场可见**而不是静默串号

## 2. 四条检测 + 一个版本探测

### 2.1 版本探测：只读，**绝不执行 claude**

`ni_probe_version()` 三条来源，全失败返回空串（调用方一律当「未知」，不因此报错）：

1. **`claude` 可执行文件解析后的路径里带版本** —— 原生安装器布局是
   `~/.local/share/claude/versions/<semver>`（本机实测：`~/.local/bin/claude` 软链到
   `.../versions/2.1.220`）。**纯 `readlink`，零执行。**
2. `<共享库>/.last-update-result.json` 的 `version_to`（成功）或 `version_from`（失败时的当前值）
3. 探不到 ⇒ 空串

**为什么不用 `claude --version`**：那要执行用户机器上真实的、已认证的 claude。
`verify` 的契约是「不登录」，在它里面执行 launcher 是越界。

### 2.2 四条检测

| # | 检测 | 档位 | 为什么是这个档 |
|---|---|---|---|
| **D1b** | **`secret` 项出现在共享库里** | **vfail** | 共享集是 `@auto`（共享库顶层 − 隔离集 − 排除集）⇒ 它会被**自动 symlink 给每个账号** = 静默串号。**这条零误报**：全迁之后 secret 本就不该在共享库里。此前只查 `.credentials.json`，从声明派生后 `.claude.json`（同样含 `oauthAccount`）也覆盖 |
| **D2** | 共享库顶层出现**声明之外的 mode 600 文件** | vwarn | 捕捉「Claude Code 开始写一个新的身份文件」——它会被自动共享给所有账号。600 是启发式（Claude Code 写凭据用 600）⇒ 只报提示。**误报的代价远小于漏报** |
| **D3** | 当前版本 ≠ manifest 里钉的版本 | vwarn | 要求人复核声明还成不成立。**版本是给人看的上下文，不是自动迁移的触发器** |
| **D4** | 声明项在共享库 / `$HOME` / 所有账号里都找不到 | vwarn | 见 §3——它**本质含糊**，判致命会让几乎每台干净机器都红 |

### 2.3 版本钉

`manifest_render` 加 **additive** 的 `claudeVersionPinned`（探不到就**省略这个键**——
「没钉」与「钉了空」语义不同）。cc-monitor 侧 serde **无 `deny_unknown_fields`**（已核）
⇒ 旧 monitor 忽略该字段，安全，**不 bump manifest `version`**。

## 3. 我把 D1 写成致命，沙盒当场误报 4 条

初版 D1 是「声明项哪儿都找不到 ⇒ **vfail**」。跑既有套件：**4 条红**。

根因：声明里好几项是 Claude Code **懒创建**的——`policy-limits.json` 撞到限速才出现、
`stats-cache.json` 用过才有。**「还没被创建」与「改了位置」从这个信号里分辨不出来。**
判致命会让几乎每台干净机器都红。

⇒ **D1 降级成 vwarn（D4），措辞如实写明这个歧义**；致命档换成 D1b（secret 在共享库里），
那条**零误报**且直指最坏情形。

这正是累积方法论里那条「**改判据前先想在野环境会不会突然多出一个红**」——
Z06 靠它没去收紧 `verify`，本轮我自己又栽了一次，被既有套件当场接住。

## 4. 两个测试泄漏真机状态的坑

写 Z07 的断言时连踩两次「沙盒没隔离干净」：

1. **往共享库放新文件后没 `sync`** ⇒ 账号还没链上 ⇒ 触发的是**既有**的「共享项缺失」检查而
   FAIL，跟 Z07 无关。修法：先 `sync --apply`，再验「已正常共享但它是个 600 的未声明项」。
2. **沙盒 PATH 不遮蔽 `claude`** ⇒ `ni_probe_version` 的第一条来源找到**真机**那个
   `~/.local/bin/claude`（软链到 `.../versions/2.1.220`）⇒ 测试读到真机版本、结果不确定。
   修法：沙盒里放一个 `$SB/bin/claude` 假二进制遮蔽掉，版本只从沙盒的
   `.last-update-result.json` 来（用 `9.9.1`/`9.9.2` 这种一眼假的值）。

两条都写进测试注释了。

| **B** | `ni_probe_version` 恒返回空（模拟探测坏掉） | **成立**：红 3 条（钉不进 manifest / 版本一致时不说一致 / 版本变化不打新旧值）。**且「探不到版本时明说跳过」那条仍绿** ⇒ 证明降级路径是被设计过的，不是碰巧 |

### 6.2 主计划成功标准 8 的达成情况，如实说

原文：「**换机制会被当场检测到**：声明绑 Claude Code 版本；实际布局与声明不符 ⇒ 报，
**绝不静默**」。

- **「绝不静默」达成**：D1b（致命）+ D2/D3/D4（提示）四条都会打印。
- **「实际布局与声明不符 ⇒ 报」部分达成**：能报的是「secret 泄漏进共享库」（致命）与
  「声明项缺席」（提示）。**不能**在「文件还没被创建」与「文件被改名了」之间做出判断——
  §3 论证了那在这个信号层面**不可判定**。
- ⇒ 主计划那句「把声明改成一个假位置 ⇒ `verify` **当场红**」**需要限定**：假位置会让
  D4 报提示（不是 FAIL）；真正的红需要 secret 真的泄漏进共享库。**已回写主计划。**
