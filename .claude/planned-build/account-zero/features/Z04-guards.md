## 1. 开工复测：计划的三条，**三条都与实际不符**

计划原文（MASTERPLAN §1 Z04）：「禁显式 `CLAUDE_CONFIG_DIR=~/.claude` 起账号 0；`verify` 新增
「`~/.claude/.claude.json` 出现」检查；「删除账号 0」特判防连带删共享库」。逐条实测：

| # | 计划说 | 实测 | Z04 实际做 |
|---|---|---|---|
| 1 | **禁**显式 `CLAUDE_CONFIG_DIR=~/.claude` | 工具**禁不了**用户的 shell。而它自己的三个入口一句话都不说：`which` 报 `d (默认)` **rc=0**、未登记时报 `(未登记的 config-dir:…)`、`run <in-place>` 直接就起 | 改成**说清楚**：三处都点名「**这不是账号 0**」+ 代价。**不禁 in-place**（它是被支持的逃生口，`init` 那里就 warn 过） |
| 2 | `verify` 新增「`~/.claude/.claude.json` 出现」检查 | **Z01 已经以 `vfail` 实现了**（比计划的 vwarn 更强）。但**只在有隔离账号时**——纯 in-place 库里整条 `skip` | 补上 in-place 那条腿：查**两份 `.claude.json` 是否同时存在** = 真分裂 |
| 3 | 「删除账号 0」特判防连带删共享库 | **早就有了**：`cmd_rm` 的 `is_under "$cfgdir" "$ACCTS_DIR"`（Z01 又加了 `rm 0` 的拒绝）。而且**还有第二道**（见 §4）。但**两道都零断言** | 钉住 |

⇒ **Z04 的实质不是「加三个守卫」，是「让已有守卫的盲区可见 + 给零断言的守卫补网」。**

## 2. 真正的洞（计划没提，实测撞出来的）

**纯 in-place 库里，`.claude.json` 的真分裂今天完全不可见。** 实测输出：

```
! 存在 in-place 账号(config-dir == 共享库):该模式下 .claude.json 会分裂,cc-monitor 不支持
- 全部账号都是 in-place,跳过「共享库应无账号态」检查
✔ 隔离项 .claude.json 是本账号私有实体          ← 共享库那份被报成**绿灯**
```

三件事凑在一起：

1. 那句 vwarn 是**泛泛的模式警告**——它说「会分裂」，**不查有没有真分裂**；
2. Z01 那条 `vfail`（home 根 secret 出现在共享库）只在 `isolated_any=1` 时跑，纯 in-place **整条 skip**；
3. 「隔离项 `.claude.json` 是本账号私有实体」这条**如实地**把共享库那份报成绿——
   对 in-place 账号而言它**确实**是私有实体。

⇒ `$HOME/.claude.json` 与 `<共享库>/.claude.json` 同时存在时，`verify` 一个字都不说。

**这正是 §0.1 那条定义在防的东西**：设了 `CLAUDE_CONFIG_DIR` 读前者、裸起读后者，
**同一个人两套 `projects` 信任 / `oauthAccount` / `numStartups`**。

### 2.1 一个把断言写错又改正的地方

初版我给这条写的断言是「纯 in-place 库里 `verify` 仍单独报『账号 0 已登录』」。**写错了**：
in-place 账号与账号 0 读的是**同一份** `.credentials.json`（共享库那份），分开报会让人以为是两个登录。

正确的事实是 **「一个登录身份、两套状态文件」**，已经写进告警措辞本身：

> …**凭据却是同一份**（`<共享库>/.credentials.json`）⇒ 一个登录身份、两套本机状态。
> 换句话说 in-place 账号与账号 0 在这个库里是同一个登录、不同的状态文件。

### 2.2 档位：vwarn 不是 vfail

in-place 是工具自己给的逃生口，用它的人可能明知代价。判致命会让**在野所有 in-place 用户的
`verify` 突然红** —— 风险不对称（本工作区那条「改判据前先想在野环境会不会突然多出一个红」，
Z06/Z07 各用过一次）。

## 3. 三处「说清楚」

| 处 | 情形 | 现在说什么 |
|---|---|---|
| `verify` | in-place 且**两份都在** | 点名两个路径 + 各自字节数 + 哪条路读哪份 + 凭据是同一份 |
| `verify` | in-place 但**还没**分裂 | 「现在**还没**分裂 —— 但只要有人裸起一次 claude 就会」（不喊狼来了） |
| `which` | `CLAUDE_CONFIG_DIR` 指向共享库、**且已登记**（in-place 逃生口） | 仍报账号名 + rc=0，**追加**「这是 in-place(V1)，**不是账号 0**」 |
| `which` | 指向共享库、**未登记**（**最危险那种**：手工设，以为这就是账号 0） | 「**这不是账号 0** —— 账号 0 是**什么都不设**」+ 给出正确起法（`run 0` / `0cc`）+ rc≠0 |
| `run` | 起一个 in-place 账号 | **不禁**（逃生口要保持可用），但把「两份状态」的代价说在前面 |

**为什么区分「已登记」与「未登记」**：前者是用户明确选过的逃生口，后者是**误以为在起账号 0**——
后者才是 §0.1 那条定义要防的误解，措辞要重得多。

## 4. ★ 变异验收撞出的事实：共享库有**两道**独立守卫

| 变异 | 做了什么 | 结果 |
|---|---|---|
| **A** | 分裂检测关掉（`if false`），退回只念模式警告 | **成立**：红 5 条（真分裂被点名 / 两个路径都打出来 / 说清哪条路读哪份 / 凭据同一份 / 与账号 0 同一个登录） |
| **B** | 拿掉 `cmd_rm` 里的 `is_under` 前置守卫 | **只红 1 条**（「rm in-place 账号被拒」）；**「共享库整个还在」没红** |
| **C** | 拿掉计划执行器 `RM)` 分支里的 `is_under` | **成立**：红「守卫层 2」 |
| **D** | `which` 对「未登记地指向共享库」不再说话 | **成立**：红 2 条（明说这不是账号 0 / 给出正确起法） |

**变异 B 值得单独记。** 我先当它是弱绿去查，手工复现后看到：

```
error: 拒绝删除 ACCTS_DIR 之外的路径:/tmp/…/.claude
删之后: 共享库 在  foo.md 在
```

`lib.sh` 的 `_exec_op RM)` 分支**自己也查一遍** `is_under "$a" "$ACCTS_DIR"`。
⇒ **「共享库还在」这条断言在那次变异下没变红，而那是正确的** —— 纵深防御生效了，不是断言弱。

第二道从 CLI **走不到**（`sync` 只会 plan RM 账号目录内的东西）⇒ 用**扫源码**的方式钉它存在
（同 `TMUX_LS_FMT` 双写点那条守卫的做法），外加一条反向自检确认两条 `grep` 真读到了文件。

## 5. 一个与 Z04 无关、但会污染判色的既有致命

沙盒的 `.credentials.json` 是默认 umask 造的（664）⇒ `verify` 有一条既有致命
「凭据权限必须 600」。不先 `chmod 600`，「只提示不判 FAIL」那条验的就不是 Z04 的判据。
已在测试里 `chmod` + 写明理由（判色三步①：先确认判的是自己那条）。

## 6. 反向自检：守卫**不许误伤账号 0**

Z07 对 D1b 犯的就是这类错（一条对合法状态恒红的检查）。本轮三条守卫逐条验：

- `run 0`（且调用者环境里带着 `CLAUDE_CONFIG_DIR=<共享库>`）⇒ **不**冒出 in-place 警告，
  且仍然 `CFG=<unset>`
- `which`（未设）⇒ 报账号 0，**不**冒出「这不是账号 0」
- 账号 0 不进 `MF` ⇒ 永远不会让 `inplace_any=1`，分裂检测不可能因它触发
