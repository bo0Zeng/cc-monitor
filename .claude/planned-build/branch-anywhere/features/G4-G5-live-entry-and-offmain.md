# G4 + G5 — 实时会话入口 · 废弃分支的呈现区分

两个都是纯前端、互相咬合（同一个按钮组件），一轮做完。

## §1 G4：钩子早就在共享层，只是没人传

`onCardRendered` 本来就在**共享**的 `render-stream-record.ts:172`，
**只有 `session-viewer` 传了它** ⇒ 实时 tab 上没有入口。

所以 G4 的实质不是「加功能」，是**把按钮抽成一份、两边都传**（主计划 §3 账本第 3 行）。

`tabs.ts` 有**两条**渲染路径，都要接：
- 单条实时渲染：`payload` 就在作用域里，直接用 `payload.path`。
- 批量渲染：`sink` 建在循环外 ⇒ 用一个**随迭代更新的游标**把当前 payload 带进钩子。
  渲染是同步的，游标不会串批。

**只对本地会话**（`tab.origin` 非空即关）：`create_branch_session` 走本机 claude 目录，
远端会话的 jsonl 在远端机器上够不着 —— 那条路由 G6 接 daemon 的 `--fork-session`。

## §2 G5：判据不重算主线，**读它的效果**

账本第 6 行要求「读 `computeMainBranch`，别另算一份主线」。这里做得更彻底：
**完全不碰主线集合**。

`BranchFolder` 已经把 off-main 的连续卡片包进 `.branch-fold-wrap` 了，
而那个包装**本身就是** `computeMainBranch` 的产物。

⇒ 判据 = `btn.closest(".branch-fold-wrap") !== null`。三个好处：

1. **不可能与主线判定漂移** —— 它就是那个判定的结果。
2. **永远最新** —— 一条现在 on-main 的消息，被 ESC 回退之后会被重新包进 wrap，
   呈现自动跟着变，**不需要任何刷新管线**。
3. 样式那半可以纯 CSS 后代选择器搞定（`.branch-fold-wrap .viewer-branch-btn`），
   零 JS 状态。

**tooltip 必须惰性**：在 `mouseenter` / `focus` 时才定。attach 时定死会说谎 ——
一条消息的主线归属会随后续对话变化。变异 Q2 钉住这点。

## §3 呈现怎么区分（用户拍板「要给路口」）

- 样式：虚线边 + 警示色 + 一个 `↩` 角标（**不 hover 也看得出**这条不是主线）。
- 文案：「⚠ 这条属于**被 ESC 回退掉的**分支。分叉会把那条你当初放弃的对话复活成一个新会话
  （原会话仍然不变）。」

**没有加二次确认**：用户原话是「缺的是信息不是限制」。能力一点不减。

## §4 实时会话的文件还在长

`branch_output_is_stable_while_source_keeps_growing`（在 `branch-core` 里）：
分叉之后往源里追加「对话继续 + 又一条 ESC 旁支 + 一条无 uuid 旁挂」，
同一分叉点的产出**逐字段相同**。

祖先回溯只依赖被选节点及其祖先，那些在选中那一刻都已落盘；后续追加都在分叉点**之后**，
不可能成为它的祖先。这条不是理论推演 —— G4 之后用户会在**正在写的文件**上点分叉。
