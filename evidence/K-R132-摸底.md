### 1.1 🔴 结论落在 `§0b` 那个问题上：**强默认不推翻**

用户逐字：「**如果有需要动用户 alias 的就生成命令让用户自己填。像是原本的填 PowerShell profile 和 bashrc 一样。**」

**现打确认「PATH 与 alias 是不是同一类东西」——答案是：在本条禁令的射程上，是同一类，而且 PATH 更重。**

- 那条禁令承重的不是「alias」这个词，是 **「产品替用户决定往他自己的配置里塞什么」**
  （`INVARIANTS.md §41.6` 的措辞就是这一句）。用户级 PATH 是**同一类东西的更重的一份**：
  alias 只影响一个 shell 的一个名字，PATH 影响**这个用户此后启动的每一个进程**。
- **业界常规那一侧我也如实说**：装 CLI 时改用户级 PATH 确实是常规（rustup / Node MSI / Python 安装器都做）。
  但**做得体面的那几家都带一个勾选框**（Python 那个 `Add python.exe to PATH` 默认**不勾**），
  也就是说：**常规的是「问过之后改」，不是「默默改」**。
  而「生成一条命令让用户自己跑」是同一件事的更强形式 —— 它连勾选框都不用，用户看得见要跑的是什么。
- **本仓这一侧还有一条硬的**：`§2` 明令「改安装器（`.nsi`/`.wxs`）等于改发版产物的形状，那是定框级的」。
  路线 ①② 真要做成「装的时候自动加」，落点就在那一族 ⇒ **不是实现方能自批的**。

⇒ **不推翻。** 本件采用的形状：

1. **产品自己动手的那一半，只动「本会话」**：PowerShell 块里多一段
   `$env:PATH = "$ccmBinDir;$env:PATH"`（幂等、按 `;` 切开比整格、装在同一对围栏里所以卸得掉）。
   它**一个字节都不写注册表**。这与 POSIX 那一臂 `shared/ccm-aliases.sh` 里那一行
   `case ":$PATH:" in … export PATH=…` **同职、同形状**。
2. **要动用户级 PATH 的那一半，生成命令交给用户**：`render_user_path_setup_command()`。
   它是三种 shell 里**唯一**能让 `cmd` 也找得到的那条路，而它由用户自己按下回车。
   两个经典地雷在生成的那几行里被绕开，并且有判据在数（不用 `setx` · 只读 `'User'` 那一档）。

⚠ **它买不到什么，写在这里**：这条命令今天**只落在用户 profile 的注释里**（安装块内、卸载时一起剥）。
**UI 上那一格没有** —— 要在「终端集成」那一块把它显示出来 ＋ 一个复制按钮，落点是
`src/launcher-diagnostics.ts`，**在 `§2` 之外** ⇒ 交回 PM 裁（见上报口）。

## 三 · `KR132D3`：`cc` / `cct` 两个名字

**`cc` —— 该改成走 `ccm`，但本轮没改，理由三条（都可证伪）。**

今天 PowerShell 这一臂是 `& claude $RemainingArgs`：**绕过后端直起 agent**。

直接后果：账号 / 工作目录 / agent 选择这几维，Windows 用户整条够不着。

本轮**不改**：
1. 🔴 **改了会是一次真的回归，而且它的前提我刚在真机上量翻过**：`& ccm` 要 `ccm` 找得到，
   而 §4 那条编码缺陷刚修，**修完的形状还没跑过一整趟真装机**。先改 `cc`，
   等于把「cc 彻底不能用」压在一个还没复验的前提上。
2. **落点在写区之外**：`launcher_identity_registry` 把 `& claude $RemainingArgs` 登记成
   「`T2` · Windows 终端里的那一下」的锚点 —— **那条登记当场逮住了我**
   （`the_terminal_launchers_are_still_where_the_registry_says`：`left: 0, right: 1`），
   它的报文自己写着「**少了** = 这条终端启动器搬家或退役了 ⇒ **来本表改登记**」。
   那张表在 `§2` 之外。
3. **它是发版产物的行为变更**，不是实现细节。

⇒ 本件把它做成**反向锚点**（判据 `the_powershell_cc_still_bypasses_the_backend_and_that_is_registered_not_forgotten`）：
它钉住「今天不一致」这件事，**翻正的那一拍必须同时做三件事** —— 改这一行 · 改那条 `T2` 登记 ·
在真机上把 `cc` **真跑一趟**（不是只看它「找得到」）。删掉这条判据让今天好过，不是出路。

## 四 · 🔴 真机逮到的第二条缺陷：**BOM-less UTF-8 ＋ PS 5.1 ＝ 静默吞掉一行**

**它不是推理出来的 —— 是修完不管用、回头查才查到的。**

把 PATH 那一段加进块里、在真机上装好、开新 PowerShell ⇒ **`ccm` 照旧找不到**。查：
`$ccmBinDir` 是空的，而 `$env:PATH` 前面多了一个 `;` ⇒ **赋值那一行没执行，`if` 那一行执行了**。

**注释行与它下面那一行被并成了一行** ⇒ 赋值落进了注释里。`parse-errors=0`，**一个报错都没有**。

**机制**：`atomic_write_string` 走 `std::fs::write`，写的是**不带 BOM 的 UTF-8**；
而 **Windows PowerShell 5.1 把不带 BOM 的 `.ps1` 按系统 ANSI 代码页解**（这台机器是 GBK）。
一个 UTF-8 的 CJK 字符被当成 GBK 解，末尾会剩一个落单的前导字节，它把紧随其后的换行吃掉。

⇒ **在 CJK 代码页的 Windows 上，「终端集成」那套窗口绑定一直是坏的**
（`$ccmDir` 为空 ⇒ `Join-Path $null …`；`$deadline` 为空 ⇒ 等待循环立刻退出），
**而它坏得很安静**：没有报错、没有解析错误。

⚠ **分母**：我量的是**一台**机器（win11 VM，系统代码页 GBK）。
「所有 CJK locale 都这样」**我没量，别那么写**；英文代码页（1252）上这条机制不成立 ——
那也正是它一直没被发现的原因。

### 4.2 修法与复验

只给 **PowerShell 那一支**加 BOM（`encode_for_disk` / `strip_bom`，落在**方言**这一层）。
⚠ **不能加在 `atomic_write_string` 里** —— 它还有两个调用方（`mcp.rs` 写 `.mcp.json`、
`account_aliases.rs` 写一份 shell 脚本），给 JSON 和 `.sh` 加 BOM 是把病传给别人。

真机复验（同一份内容，只在前面加三个字节 `EF BB BF`）：

| | `ccm`（PowerShell） | `$ccmBinDir` | 进程 PATH |
|---|---|---|---|
| 无 BOM | NOTFOUND | **空** | 多了一个裸 `;` |
| 有 BOM | ✅ `C:\Users\VM260726\.cc-monitor\bin\ccm.exe` | 正确 | 头部多了那个目录 |
