## 二 · 清单（逐条）

### R1 · 裸 `monitor.exe` 自己把本机后端释放出来〔类 B〕

- **做什么**：干净 Windows 机，**只放** Release 页上的 `monitor.exe`（不装 NSIS / MSI），双击起。
- **期望看到**：任务管理器里出现 **1 个** `cc-monitor-*` 后端进程；app 的「机器」里本机那台标着后端在跑；
  `%USERPROFILE%\.cc-monitor\bin\` 下多出自释放的那份二进制。
- **看不到说明**：`release.yml` 的 `Stage native daemon for self-extract` 那步没把
  `src-tauri/native-daemon/cc-monitor-native` 铺进去（`build.rs::embed_native_daemon()` 于是静默不置 cfg），
  或自释放在 Windows 上跑不通 ⇒ 回到 `release.yml` 那句逐字的「**0 个本机后端进程**」。
- **门禁为什么答不了**：`Stage native daemon for self-extract` 是 `v3.7.0` 之后才加的一步
  （`git diff v3.7.0..HEAD -- .github/workflows/release.yml` 里新增的**唯一**一个 `- name:`），
  **一次都没在 tag 上跑过**；而本机门禁那棵树 `cfg(embedded_native_daemon)` 未置 ⇒ 那 16 处一行都没编。

### R2 · `ccm` 这条命令行入口（旧的那 1592 行 bash 已经删了）〔类 B+C〕

- **做什么**：干净机器装完，**开一个新 shell**，依次跑 `ccm --ccm-probe`、`cc --help`、`cct --help`。
- **期望看到**：`--ccm-probe` 吐六行（`name= / version= / self= / capabilities= / agents= / build=`），
  其中 `build=p2j-bus-state`；`cc` / `cct` 都能起会话。
- **看不到说明**：`install_local_ccm_entry` 没把入口铺到 `~/.cc-monitor/bin/`，
  或别名块没接上 PATH ⇒ 用户装完了敲 `ccm` 什么都没有。
- **门禁为什么答不了**：`shared/ccm` 那份 bash **09-12 删了**（`e8f9e08`，−1592 行），
  今天的 `ccm` 是**后端二进制的改名副本**，而「把它铺到用户家目录并接进 PATH」这条路
  在沙箱里够不着（类 C）。四套 ccm e2e 测的是**命令串怎么渲染**，不是**入口铺没铺**。

### R3 · 升级用户身上那份**旧 `ccm`** 会不会把新的挡住，产品说不说得出〔类 C〕

- **做什么**：一台**装过 `v3.7.0`（或更早）**的机器上升级，别删任何东西，开新 shell 敲 `which -a ccm`；
  再打开 app 看「本机 / 启动器诊断」那一块。
- **期望看到**：`which -a ccm` 大概率**两条**（`~/.local/bin/ccm` 那份旧 bash 在前）；
  ⇒ app 里必须出现那句判词（`PathCcmVerdict::NotOurs`，话里同时带 `version=4` 与 `version=5`，
  **且不含「请删除」**）。
- **看不到说明**：`classify_path_ccm` 在真机上探不到旧的那份（探针只在单测夹具上活过）⇒
  用户敲 `ccm` 走的是旧 bash，而产品一声不吭 —— 这正是 `K34`「旧的那份能**干净退役**」要挡的那一格。
- **门禁为什么答不了**：这一格的输入是**用户机器上历史遗留的那个文件**。沙箱 `HOME` 几乎是空的
  （类 C），构造不出「PATH 上另有一个也叫 ccm 的东西」这个前提。

### R4 · `cch` 这个别名删了，而它已经写进老用户的 shell 配置里〔类 C〕

- **做什么**：同 R3 那台升级机，开新 shell，`type cch`。
- **期望看到**：要么 `cch: not found`，要么是用户自己定义的那一份。
- **看不到说明**：仍然看到 `cch () { ccm --cwd . "$@" }` ⇒ 那份 `ccm-aliases.sh` 在升级时没被重写，
  用户手上握着一个指向**已删语义**的别名（`--cwd .` 今天与不给一模一样）。
- **门禁为什么答不了**：被测对象是**用户 rc 里已经存在的那几行**，不在仓里。
  `profile_installer::scan_legacy_rc_lines` 有单测，但它的输入是夹具。

### R5 · 已装过 daemon 的远端会被判旧、自动重装一次〔类 C+D〕

- **做什么**：一台**用 `v3.7.0` 部署过 daemon** 的 Linux 远端；升级 app 后连上去，全程看部署日志。
- **期望看到**：连接过程里发生**一次**重新上传 + 重启；之后远端 `ccm --ccm-probe` 报
  `build=p2j-bus-state`；会话列表、抓屏、起会话都正常。
- **看不到说明**：部署决策那条路坏了 ⇒ 远端一直跑着旧 daemon（`p2e-dial`），
  而新前端会对它发它**不认识**的帧（`capture-pane` / `bus-*` 那几条），症状是「界面上某一块空着，没人报错」。
- **门禁为什么答不了**：`BUILD_ID` 从 `p2e-dial` 变成了 `p2j-bus-state`
  （`git show v3.7.0:remote-daemon-proto/src/main.rs` vs 盘上，两侧现打）——
  「判旧 → 重传 → 重启」整条链要一台**真的装过上一版**的远端才跑得出来。

### R6 · aarch64 远端上，那份 musl daemon **跑不跑得起来**〔类 C〕

- **做什么**：一台 arm64 Linux 远端（树莓派 / arm 云主机），在 app 里配上去，让它自动部署；
  然后起一个会话、看一次用量、让中转发一次 https 出站。
- **期望看到**：daemon 起得来；`--ccm-probe` 报得出 `build=`；会话与抓屏正常；
  https 出站握得上手（**不是**读配置，是真连一次）。
- **看不到说明**：aarch64 + musl 的**运行期**缺东西 —— `ring` 的 aarch64 汇编 / musl 的 DNS 解析 /
  没有 `/etc/ssl` 时靠 `webpki-roots` 顶上这几条里的某一条。
- **门禁为什么答不了**：🔴 **本件今天买到了两格半**（读数住 `evidence/K-R114-deathvalue.md#三`）：
  ① 编得出（aarch64 · 静态 musl）· ② 信任锚在产物字节里 ·
  ③ **在 `qemu-aarch64` 用户态模拟下跑得起来**，进程自报 `host_arch=aarch64` /
  `build_id=p2j-bus-state`，`argv[0]=ccm` 时 `--ccm-probe` 六行都答得出来。
  **仍然判不了的是**：真 aarch64 **内核**上对不对（qemu-user 的系统调用走的是这台 x86_64 内核）·
  **TLS 一次都没真握手过**（那一趟 `--network none`）· 没有真 tmux / 真 `~/.claude`。
  ⇒ 本条留在表里的就是这三样。

### R7 · 用量面板改走 `capture-pane` 帧之后，数字还出不出得来〔类 D〕

- **做什么**：真机上起一个真 `claude` 会话，等它出用量，看 app 「用量」那一块。
- **期望看到**：数字出得来，且与 `claude` 自己屏幕上那一行**对得上**。
- **看不到说明**：真 daemon 的 `capture-pane` 回帧**形状**与 monitor 侧期望的不一致
  （字段名 / 换行 / 截断口径任一处）⇒ 用量恒空或恒零，而**两侧的单测都是绿的**。
- **门禁为什么答不了**：`K-R112` 把抓屏那条路从旧走法换成了 daemon 原语
  （`src-tauri/src/account_usage.rs:291` 的 `ch.call("capture-pane", …)`）。
  monitor 侧的夹具是它自己造的假 channel，daemon 侧的夹具是它自己造的假 tmux ——
  **两边同时错成同一个形状，门禁两边都绿**（类 D）。

### R8 · cc-bus 三条（发 / 名单 / kill）改走原语之后，真 tmux 上还灵不灵〔类 D〕

- **做什么**：真机起两个会话，用 cc-bus 面板：向另一个广播一条 → 看名单 → kill 掉一个 → 再看名单。
- **期望看到**：另一个会话**真的收到**那条消息；名单里两条都在；kill 之后名单少一条。
- **看不到说明**：`bus-send` / `bus-list` / `bus-kill`（`src-tauri/src/cc_bus.rs:1323/1328/1331`）
  这三条原语在真 daemon + 真 tmux 上的行为与夹具不同 —— 最可能的形状是
  「面板上看起来发出去了，对面没收到」。
- **门禁为什么答不了**：同 R7 的类 D。另外沙箱里那个 tmux 是容器自己的，
  够不着「用户机器上真正在跑的那些会话」（`gate` 头注：不挂 `/tmp/tmux-1000`）。

### R9 · `bus-state` 这条新 RPC，在真 daemon 上答不答得出来〔类 D，且**今天连接线红都不会有**〕

- **做什么**：对一台**已经部署了这一版**的 daemon，直接发一帧 `bus-state`
  （`ccm` 那条入口或协议客户端都行），读回包。
- **期望看到**：一份**非空**的总线名单 ＋ spawn 台账；名单里的会话名与 `bus-list` 那条对得上。
- **看不到说明**：这条原语只在单测里活过 —— 帧名、参数形、回包字段任一处与真实调用方对不上。
- **门禁为什么答不了**：🔴 **monitor 侧今天没有任何调用方**
  （`grep -rn '"bus-state"' src-tauri/src` ⇒ **0 处**；只有 `remote-daemon-proto` 那边有）。
  ⇒ 它连「接线断了」这种红都不会有：**没人接，就没人会红**。
  `K-R113` 自己的定位逐字是「真接线那 4 条里的**第 4 条的前置**」。

### R10 · `ccm attach` 那一句：本机会话点「接入」真的接得进去〔类 A+C〕

- **做什么**：本机（Windows）起一个 tmux 会话，在会话列表里点「接入 / attach」。
- **期望看到**：终端真的接进那个会话；那条命令串形如 `ccm attach <名>`，**由后端产**。
- **看不到说明**：要么 `render_local_attach` 没注册进 Tauri handler（`src-tauri/src/lib.rs:1300`），
  要么产出的串在这台机器上**不可执行**（`ccm` 不在 PATH ⇒ 与 R2 / R3 同源，
  而症状会显示成「attach 这个功能坏了」，把人引到错的地方）。
- **门禁为什么答不了**：调用点在 `src/remote-launch-run.ts:519`，前端侧是 vitest 的假 `invoke`；
  Rust 侧是 `cargo test --lib`。**「Tauri 把这两半接起来之后还通不通」没有任何一格在看**
  （类 A：那一跳只在真 WebView 里发生）。

### R11 · Release 页上那个安装器本身装不装得上、内嵌全不全〔类 B〕

- **做什么**：从 Release 页下 `-setup.exe` 与 `SHA256SUMS.txt`，**先核校验和**，
  再在干净 Windows 机上装一遍，打开 app 看「自动部署」那一格。
- **期望看到**：校验和对得上；装得上、起得来；「自动部署」是**开着**的（不是「诚实关闭」）。
- **看不到说明**：`Place + verify embedded daemons` 那一步这一轮**判法整个换了** ——
  从「读旁边那个 `.build_id` 清单文件」换成「**从二进制字节里扫身份戳**」
  （`git diff v3.7.0..HEAD -- .github/workflows/release.yml`：`.build_id` 那三行删了，
  换成 `BUILD_STAMP_OPEN/CLOSE` 拼出来的 `$want` 在字节里 `IndexOf`）。
  它坏 ⇒ 要么发版当场红（好），要么内嵌没进去而检查恒真（坏）⇒ 远端自动部署静默降级。
- **门禁为什么答不了**：这一步只在 `release.yml` 里，本机一步都跑不了（类 B）。
  🔴 **本件今天把它往前推了一格**：`workflow_dispatch` 那一趟演练**真的跑了这一步**
  （run id 与逐步结论见 `§3`／`evidence/K-R114-deathvalue.md`），
  但演练**不产出安装器给人装** —— 「装得上」那一格仍然只有真机能答。

### R12 · 版本号今天还是 `3.7.0`〔不是清单条目，是**发版前的阻塞项**，写在这里免得掉了〕

`package.json` 现打 `"version": "3.7.0"`，而 `v3.7.0` 已经发过。
`release.yml` 的「四处版本号与 tag 一致」那道门 ⇒ **拿今天这棵树推 `v3.8.0` 会当场红在那一步**。
🔴 **本件明令不改版本号**（`§2` 写死）⇒ 端给 PM：发版那一拍要先 bump 四处
（`package.json` · `src-tauri/tauri.conf.json` · `src-tauri/Cargo.toml` · `src-tauri/Cargo.lock` 的 `monitor` 包）。
⚠ 顺带一条同族的：`CHANGELOG.md` 最上面一节还是 `[3.7.0] — 2026-09-10`，**这 230 个提交一条都没进去**。

### R13 · 🔴 `npm run build` 今天**编不过** —— 发版流水线在这里死〔不是清单条目，是**已经发生**的阻塞项〕

**这一条不是「真机才能验」，是「今天就红」，而且是本件那一趟 `workflow_dispatch` 演练当场逮到的。**

`release.yml` 的 `tauri build` 调 `beforeBuildCommand` = `npm run build` = `tsc && vite build`，
云端逐字 6 条 `TS2322`（`src/views/history.ts` 的 1601/1603/1640/1642/1838/1839），退出码 2；
**沙箱里重打同形**（`npx tsc --noEmit` ⇒ 同样 6 条、`TSC_EXIT=2`）。
根因与住址、引入于哪个提交、门禁为什么全绿 —— 逐条写在 `evidence/K-R114-deathvalue.md` 的 `§2.5`。

一句话：**13 格门禁的 `npm` 那一格跑的是 `npm test`，不含 `tsc`**；
而云端 `ci.yml` 里那条 `npx tsc --noEmit` 只在 `main` / tag / PR 上跑，
**这 210 个提交一次都没进过 `origin/main`** ⇒ 它一次都没跑。
🔴 本件不修（`src/**` 明令不在写区）。**发版前必修，否则连安装器都产不出来。**
