## 一 · 台架自己会让宿主 `ip link` 多出什么 —— 逐类，带名字形状与出处行号

现打 `e2e/weak-net/rig.sh` 全程（行号量于本件改完之后那一版）：

| # | 类 | 名字形状 | 出处行号 ＋ 逐字校验位 | 个数 |
|---|---|---|---|---|
| 1 | 自建网络的**宿主 bridge** | `br-<网络 id 前 12 位十六进制>` | `:259` `docker network create "$NET" >/dev/null 2>&1 \|\| { no "建自建网络失败"; finish 3; }` | **1** |
| 2 | 容器 veth 的**宿主端** | `veth<7 位十六进制>@if<容器内 ifindex>`，且 `master br-<同上>` | `:261` `docker run -d --name "$CB" --network "$NET" "$IMG" sleep infinity >/dev/null 2>&1 \` · `:264` `docker run -d --name "$CA" --network "$NET" --cap-add=NET_ADMIN "$IMG" sleep infinity >/dev/null 2>&1 \` | **2** |
| 3 | `netem` / `tbf` **挂载面** | —— | `:52` `DEV="eth0"` ＋ `:307` `out="$(docker exec "$CA" tc qdisc add dev "$dev" root "$@" 2>&1)"; rc=$?` | **0**（见下） |

**合计：台架自己让宿主 `ip link` 多出 3 个设备。** 收走它们的是
`:188` `  docker rm -f "$CA" "$CB" >/dev/null 2>&1` ＋ `:189` `  docker network rm "$NET" >/dev/null 2>&1`。

### 1 · bridge 的名字形状 —— 只读实测 3/3

`docker network ls --no-trunc` ＋ `ip link`（只读，量于 09-15 本机）：

| 网络 | id 前 12 位 | 宿主 `ip link` 里实得 | 该网络上的容器数 | 实得 veth 数 |
|---|---|---|---|---|
| `beszel_default` | `6e8c57c1920a` | `br-6e8c57c1920a` | 1 | 1 |
| `park-miniapp_default` | `5c45e8c5297c` | `br-5c45e8c5297c` | 0 | 0 |
| `server_default` | `c83adad1ec32` | `br-c83adad1ec32` | 2 | 2 |

**分母 = 本机全部 3 条自建 bridge 网络**（`docker network ls` 里 driver=bridge 且非预置的 `bridge`）。
3/3 命中 `br-<id 前 12>`，且 **veth 数恒等于该网络上的容器数** —— 台架「1 网 + 2 容器」
这一形的宿主对应物就是「1 bridge + 2 veth」。
⚠ **这是约定不是保证**：docker 允许用 `com.docker.network.bridge.name` 改名，台架没设。
⇒ 台架里那条 `br-<id 前 12>` **只当读数印，不参与判红**（`rig.sh:283-288`），改名了也不会假红。

### 2 · `netem` 为什么是 **0 个**

`tc` 打在**容器 A 自己 netns 的 `eth0`** 上，而容器 eth0 与宿主侧 veth 是**两个设备**。
隔离 netns 里实测（同一对 veth，规则打在对端）：

```
### A. netem 之前，宿主侧那一行
3: hostside@guestside: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue master brtest state UP mode DEFAULT group default qlen 1000
### B. 在 **对端** guestside 上 tc qdisc add root netem delay 200ms
qdisc netem 8009: root refcnt 17 limit 1000 delay 200ms
### C. netem 之后，宿主侧那一行（与 A 逐字比）
3: hostside@guestside: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue master brtest state UP mode DEFAULT group default qlen 1000
### D. 全表里 netem 出现在哪几行
3:2: guestside@hostside: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc netem state UP mode DEFAULT group default qlen 1000
### E. 反证：同一条规则打在宿主侧自己身上
3: hostside@guestside: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc netem master brtest state UP mode DEFAULT group default qlen 1000
```

A 与 C **逐字相同** ⇒ 对端的 qdisc 进不了本端那一行 ⇒ 台架的 netem 在宿主 `ip link` 里**看不见**。
🔴 而 **E 是本件最重要的一条反证**：`ip link` **确实会印 qdisc**（`noqueue` → `netem`）
⇒ 万一哪天 `--network host` 溜进来、`tc` 真打在用户的真网卡上，**宿主那一行会变**。
⇒ **「两份都有的设备逐行比」这颗牙不许拔**（本件保留了它，见 `§二·T3`）。

## 二 · 「不该进分母」那一侧的**结构性判别式**

事故里那个设备（件 `K-R136` `§0` 的 CI 原始输出，逐字）：

```
7: enP20511s1: <BROADCAST,MULTICAST,SLAVE,UP,LOWER_UP> mtu 1500 qdisc mq master eth0 state UP …
```

⚠ **不许用名字白名单** —— 已实撞两趟，名字不同：PR `#92` 是 `enP20511s1`，
`main` `7fb79638` 是 `enP29037s1`。名字里的数字每次开机都变。

**判别式（两条腿都要成立）**：

> `kernel_enslaved(rec)` ＝ 该设备 `<…>` 旗标里有 **`SLAVE`** **且** 它的 `master <X>`
> 的 `X` 在**对面那一份快照**里（新出现的设备看**前**一份，消失的设备看**后**一份）。

住址：`e2e/weak-net/rig.sh:156` `    function kernel_enslaved(rec, where,   m) {`（全仓唯一一处）。

**两条腿都是实测的**，隔离 netns，量于 09-15：

| 造法 | 实得那一行 | 有 `SLAVE` 吗 |
|---|---|---|
| `ip link set <veth> master <bridge>`（**docker 的形状**） | `4: vhost@vguest: <BROADCAST,MULTICAST,M-DOWN> mtu 1500 qdisc noop master brtest state DOWN …` | **没有** |
| `ip link set <dev> master <bond>`（**VF 的形状**） | `3: vguest@vhost: <NO-CARRIER,BROADCAST,MULTICAST,SLAVE,UP,M-DOWN> mtu 1500 qdisc noqueue master bondtest state LOWERLAYERDOWN …` | **有** |

⇒ 网桥端口走的是 `bridge_slave`，内核**不置** `IFF_SLAVE`；bond/team/VF 那一族才置。
Azure 加速网络的 VF 由 `hv_netvsc` 做**透明绑定**，落在后一形
（`enP20511s1` 那一行 `SLAVE` ＋ `master eth0` 逐字吻合）。
⇒ **台架造得出来的三类设备一个都不带 `SLAVE`** ⇒ 这一档排除**结构上够不着**台架自己的残留。

### 为什么两条腿都要，不能只要一条 —— 实测，不是论证

拿掉 `SLAVE` 那条腿（只剩「master 在前一份里就有」）＝ **刀④**。它在我全部夹具上都活着，
**只有一格杀得掉它**：残留的 veth 故意挂在跑前就有的 `docker0` 上。

| 夹具 | 本版 | 刀④（掉 SLAVE 腿） |
|---|---|---|
| 残留 veth `master docker0` | `NEW=1` **逮住** | `NEW=0` **漏掉** |
| 事故那行 VF | `NEW=0`（排除） | `NEW=0`（排除） |
| 真残留：自建网络没删 | `NEW=3` | `NEW=3` |

⇒ `SLAVE` 那条腿**是承重的**：少了它，一条挂在既有 bridge 上的残留 veth 会被静默放过。

## 三 · 🔴 判不了的那几条 —— 逐条写清「算不算残留」

1. **「docker 自己起停也会动 `ip link`」——「算不算残留」答得了，「判不判得出来」答不了。**
   · **算不算**：**不算**。别人的容器起停留下的 `vethX@ifN`，不是台架留的。
   · **判不判得出来**：**判不了。** 第三方容器的宿主侧 veth 与台架自己的 veth
     **结构上一模一样**（都是 `veth…@if<N>`、都 `master br-<某网络>`、都不带 `SLAVE`）。
     本判别式**分不开它们**。
   · **今天的实际暴露面**：GitHub runner 上台架是唯一的 docker 消费者 ⇒ 那一档人群为空；
     共用开发机上它是一处**真假红**。
   · **刻意不为它放宽**：「新设备的 master 在前一份里就有」那条挡得住它 —— 那就是**刀④**，
     而上面那张表实测它会漏掉「挂在 `docker0` 上的残留 veth」。⇒ 不采，记在这里归 PM 裁。
2. **`docker0` 的 `state DOWN`↔`UP`** 随别人的容器起停翻 ⇒ 落在「两份都有、那一行变了」（T3）⇒ 会红。
   同样**刻意不放宽**（理由见 `§一·2` 的 E 反证：放宽 T3 就等于放掉「tc 打到宿主」那颗牙）。
   共用开发机上这是一处已知假红；CI 上人群为空。
3. **第二趟（`main` `7fb79638` / `enP29037s1`）的原始 `diff` 段我没有。**
   现打 `grep -rn 'enP[0-9]' .`（分母 = 本工作树全部 `*.md` `*.rs` `*.sh` `*.yml`）⇒ **0 命中**；
   件文件 `§0` 只记了名字，没记输出。⇒ 「VF 热插拔那一趟**只会追加、不会改动既有行**」
   这句话我**只有一个观测点**（PR `#92` 那趟的 `6a7,9`，纯 append、零 `c`/`d` 段）。
   两个观测点才敢说「这一族都是纯追加」，**我只有一个，所以不说**。
4. **本判别式不防恶意**：它读的是 `ip link` 的文本，谁能改那份文本谁就能骗过它。
