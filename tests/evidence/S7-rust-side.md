⇒ **本文的每一条判断都只用「同一轮里的差值」和「数量级」，不用绝对值。**

### 4.2 `stream_from_offset`：从中位增量到 1 MiB，**量不出来**

`offset` 那五格（1 641 B → 1 MiB）的 p50 全部落在 **0.61–0.89 ms**，
与进程地板（0.63–0.99 ms）**分不开**。到 offset = 0（整文件 15.1 MiB）才涨到 **1.18 ms**。

⇒ **`§3.2`「O(新增字节)」在典型增量上成立到「量不出来」的程度。**
典型增量那一侧**没有任何可优化的余地**，一次调用的钱全花在 `fork/exec` 上（≈ 0.7 ms），
而那 0.7 ms 又完全被它前面那次 SSH 握手盖住。**这一半不用再看了。**

### 4.3 巨记录**不贵**，反而略便宜

`s7-longtail`（含 2 条 631 672 B 记录）与 `s7-main` 同字节数，耗时 **13.5–19.4 vs 13.5–19.5 ms**，
在噪声内、多数轮里**长尾那份更快**（行数少 8%）。

⇒ 取尾这一层的成本轴是**字节**，不是「有没有巨记录」。
`§1.1` 推论二（「按 617 KB 估不按 1.6 KB 估」）**对前端渲染成立，对后端取尾不成立** ——
`read_until` 把一条 617 KB 的行读进一个复用的 `Vec` 里，只多一次容量增长。
⚠ 这一条**只说取尾**。`§3.5` 那条「每条记录解析成 untyped `Value`」是另一条路，不在本秤射程里。

## 5. 反空真自检与死值验（原文）

### 5.1 反空真：输入不存在 / 是空的 ⇒ **判失败**，不是跑出个 0 ms 就绿

秤在跑任何一格之前先拿**不存在的路径**与**空文件**各验一遍它自己的检查器，
再拿同一个检查器去验真夹具；任何一条 `Err` 都 `exit(1)`。原文：

```
[反空真] 不存在的文件 → 判失败 ✓  （…/s7-does-not-exist.jsonl：取不到元数据（多半不存在）：No such file or directory (os error 2)）
[反空真] 空文件 → 判失败 ✓  （…/s7-empty.jsonl：只有 0 B，下限 1 B —— 空文件或没生成全）
```

同一个检查器再去验真夹具。把 `.build/s7/` 移走后现打（原文）：

```
秤 7：夹具不合格 —— …/s7-p50.jsonl：取不到元数据（多半不存在）：No such file or directory (os error 2)
      先跑 tests/evidence/S7-make-corpus.sh 重建。
error: bench failed …  process didn't exit successfully: … (exit status: 1)
```

把夹具换成 0 字节的空文件，**同样 exit 1**（不是「跑出个 0 ms 就绿」）。

另有两道：**每一跑的退出码非 0 当场作废**（不然一条 exit 2 的错误路径会伪装成一个漂亮的小读数）；
**出字节恒零的格会被点名告警**（`floor` 那一格除外，它本来就该是 0）。

## 6. 🔴 判决：`(size, mtime) → (total, tail_from)` 这个缓存 **不值得做**

### 6.1 今天一次调用多少 ms

| 会话大小（`§1` 那一列） | `--read-session-tail` 总耗时 p50 | 其中**数行 `K`** |
|---|---:|---:|
| 中位 990 KB | 1.6 – 2.7 ms | 0.7 – 1.5 ms |
| p90 4318 KB | 4.2 – 6.2 ms | 3.3 – 5.5 ms |
| **max 15.1 MB** | **13.5 – 19.5 ms** | **12.4 – 17.9 ms** |

max 那一档的数行吞吐跨 6 轮落在 **0.82 – 1.20 GiB/s**；三档 K 的比值 **1 : 4.6 : 17.6**
对字节比 **1 : 4.3 : 15.5**（990 KiB 那档只有 153 行、噪声占比大，偏高的那点在它身上）
⇒ **K 随字节大致线性**，`§3.1` 那句「**O(文件)**」**实测成立**。

### 6.2 一次会话里被调几次

**一次连接里，每个会话恰好一次。** 住址与证据：

- `ssh_source.rs` 的 `fetch_snapshot` 拼 `--read-session-tail <path> {SNAPSHOT_TAIL_LINES}`（`SNAPSHOT_TAIL_LINES = 500`）。
- 入队点在 daemon 宣告 `session_added` 那一处：`tail_only` 且帧带 `path` ⇒ `snapshots.push(SnapshotItem{…})`。
  ⇒ **daemon 宣告几个会话就排几项**，不是「打开哪个 tab 才拉哪个」。
- `SnapshotQueue::push` 按 sid **幂等**（`seen` 去重）；`snapshot_dispatcher` 并发 ≤ 2、失败重试 1 次。
- 会话 removed→re-added、或**断线重连**（队列 `close` ⇒「排队项作废，重连重拉」）会再来一次。

⇒ 真机那一档（`§1`：28 会话 / 47.4 MB）**开一次软件 = 28 次调用**，
数行合计 ≈ 47.4 MiB ÷ 1 GiB/s ≈ **45 ms**，由 2 个 worker 分摊。
单个会话最坏 **13.5–19.5 ms**，**一次**。

### 6.3 缓存能省多少 —— 以及它省的那一块在整条路上占多大

每次命中省 `K`：max 那档 **12.4–17.9 ms**，中位那档 **0.7–1.5 ms**。

🔴 **但它坐在一次 SSH 握手后面。** `fetch_snapshot` 每一项都走 `connect_and_exec_cmd`，
而那个函数**每次新开一条 SSH 连接**（`connect_session` → TCP → 握手 → 认证 → `channel_open_session` → `exec`）。
本轮**没量**那次握手（要真远端，见 §7），但它是**十毫秒到数百毫秒**量级的事 ——
省掉的 13 ms 落在这样一条路上，**是个位数百分比，不是可感知的改善**。

### 6.4 缓存本身的代价

#### ① 🔴 它**没地方住** —— 这一条就足以否掉

`--read-session-tail` 是**一次性进程**：SSH 起一个、吐完字节就退。
（`main.rs` 的 `SUBCOMMANDS` 表里它在查询那一族；常驻口 `ch:*` 的清单里**没有**它。）

⇒ 进程内缓存**活不过这次调用**，要跨调用就必须**落盘**。
而 daemon 的只读红线由 `readonly_guard::every_fs_call_in_daemon_production_is_read_only`
钉着：生产段每一处 `fs::` / `File::` 调用都要在**只读白名单**里，写盘白名单**恰好一个模块**
（`control/fork_write.rs`）。

⇒ 做这个缓存 = **为一个 13 ms 的优化，去开 daemon 唯一的只读红线的第二个洞。**
`Cargo.toml` 里那条「刻意不开 `creds-core` 的 `harden` feature」的理由逐字同族：
**让它写不出来，比事后检测更强。**

#### ② `(size, mtime)` 这把尺子**什么时候会骗人**

| 情形 | 为什么骗 | 这仓里真会发生吗 |
|---|---|---|
| **同尺寸重写** | `size` 一样、内容变了 | 会。写这些文件的是 **Claude Code 自己**，不在本仓控制内；而 `watcher.rs` 有**显式的截断处理**（`offsets` 重置为 0、seq 另存以免回卷）⇒ 本仓已经把「这个文件会缩、会被重写」当成真实情形认下了。⚠ 订正一处：`--fork-session` **不属于**这一族 —— `control/fork_write.rs` 只用 `create_new(true)`（`O_EXCL`）新建，不覆盖 |
| **mtime 粒度** | 1 s / 2 s 粒度的文件系统上，同一秒内的第二次写看不见 | 会。daemon 的部署目标含 Pi 级设备与网络挂载（NFS/SMB/exFAT 都不是 ns 粒度） |
| **mtime 倒流** | 同步工具**保留** mtime ⇒ 新内容配旧 mtime | 会。这台机上 `~/文档/` 正由 **Resilio** 双向同步；rsync `-t` / git checkout 同形 |
| **mtime 可被写** | `utimensat` 谁都能调，设回去就行 | 能 |
| **路径复用** | 会话删了、同名新文件顶上；key 只有 path 就撞 | 能（key 得带 dev+ino 才勉强） |

#### ③ 命中错了的**失败方向是错的**

`total` 不只是个统计数 —— `IPC-PROTOCOL.md` 逐字写着它「做**精确完整性对账**」，
而 monitor 按 `(total, tail_from)` 给两段编 seq。

⇒ 一次陈旧命中的后果不是「慢了点」，是**行号编错**或**对账假红**。
**fail-open 方向**：把一次可疑的读变成一次看起来正常的读。
`readonly_guard` 那段头注逐字讲过同一件事：白名单误配等于授权，登记表误配还要再过一道检查
—— 这个缓存属于**前者**那一族。

### 6.5 ✅ 该做的是另一件事：**改 5 行，省掉同一块的 77%**

`read_session_tail` 的扫描循环里，**每一行**都做一次
`String::from_utf8_lossy(整行)` 再 `trim()`，**只为判断这一行是不是空行**。
那是一次**整文件 UTF-8 校验** —— 0.8–1.2 GiB/s 正是这个速度。

变体 C'：先看字节短路，短路不下判才退回原判定。jsonl 每行首字节是 `{` ⇒ **第 1 个字节就短路**。

```rust
let decided = buf[..buf.len() - 1]
    .iter()
    .any(|b| b.is_ascii() && !char::from(*b).is_whitespace());
if !decided {
    /* 原来那两行，一字不改 */
}
```

| 格（max 15.1 MiB，同一轮） | A 原样 | **C' 变体** | 变化 |
|---|---:|---:|---|
| `tail N=500` p50 | 19.524 ms | **3.785 ms** | **↓ 5.2×** |
| **数行 `K`** | 17.894 ms | **2.980 ms** | **↓ 83%** |
| 另一轮（A 更快的那轮）K | 13.095 ms | 2.98–3.49 ms | ↓ 73–77% |
| `tail`〔管道〕p50 | 18.408 ms | 7.564 ms | ↓ 2.4× |
| 出字节 | 15 837 197 | **15 837 197** | **一字节不差** |

**等价性**（两道，都过了）：

1. `cargo test history_query::` —— **22 过 / 0 败**（`tail_tests` 那一族的空行 / BOM / torn 口径锚点全在里面）。
2. 穷举对拍 `tests/evidence/S7-blank-line-equivalence.rs`：
   全部 1 / 2 / 3 字节输入（**16 843 008** 个）＋ 300 万条随机 0–12 字节串，**分歧 0**。

   ⚠ 这里**必须**是 `char::from(*b).is_whitespace()`，**不能**是 `b.is_ascii_whitespace()`
   —— 后者**不含 `U+000B`**（垂直制表），而 `str::trim` 含它。第一版变体就是这么写错的，
   **靠这支穷举才逮出来**，单测没逮住（没有那个样本）。

⇒ **同一块钱，一个不用状态、不用失效判定、不碰只读红线的拿法。**

剩下的 `K ≈ 3 ms / 15.1 MiB`（≈ 5 GiB/s ≈ `memchr` 的速度）才是 `§3.1` 说的那个
**真·不可避免的 O(文件)**。对它再做缓存，省的是 3 ms，代价还是 §6.4 那三条。**更不值。**

### 6.6 一句话

> `§3.1` 的「O(文件) 不可避免」**成立**（实测线性，0.8–1.2 GiB/s）。
> 但「贵」那一半**贵在实现，不贵在算法** —— 77–83% 的扫描成本是每行一次整行 UTF-8 校验。
> ⇒ **缓存不做**（没地方住 · 尺子会骗人 · 失败方向是错的 · 省的钱被一次 SSH 握手盖住）；
> **改那 5 行值得做**（等价性有穷举证据，风险是零状态的）。

## 7. 它量不到什么 🔴

写清楚，免得下一个人把这份读数当全部：

1. **不是 Windows。** 只有 Linux。`§1` 自己也写着 Windows 那侧只跑 monitor 不产会话，
   但 daemon 有 Windows 冒烟构建 ⇒ 那一侧的数**这里没有**。
2. **不是冷缓存。** 全部热页缓存。冷缓存下扫描那一趟要真读盘，
   ⇒ `K` 会被磁盘带宽盖住，`§6.5` 那条改法的**相对**收益会变小（绝对值不变）。
   ⚠ 反过来说：`--read-session-tail` **把文件读了两遍**（扫一遍 + 拷一遍），冷缓存下
   第二遍是热的 —— 这个「两遍」的代价**本秤没有单独量过**。
3. **不过 SSH。** 表里最接近真实传输的是「管道」那两行（4.5–6.5 ms 搬 15.1 MiB）。
   真 SSH 有加密、有窗口、有网络 —— **那一段完全不在读数里**。
4. **没量 SSH 握手。** §6.3 说「13 ms 被握手盖住」是**推断**，依据是代码路径
   （`fetch_snapshot` → `connect_and_exec_cmd` → `connect_session` 每次新连），
   **不是本轮的读数**。要核它得有真远端。**这一格是「没量」，不是「量过没事」。**
5. **不是真机语料。** 合成放大，行长分布照抄、内容全假（§3）。
   真机语料里那 19% 纯元数据记录（`§1.2`）在本夹具里按同一分布带着，但**没有单独对过账**。
6. **一台手持机，散热受限。** 单格跨轮漂移 ±40%（§4.1）。`aya` 上会是另一组数。
7. **没跑 `tests/scripts/gate.sh`**（本件纪律要求）。跑过的是
   `cd src/backend && cargo test --offline` ⇒ **703 过 / 0 败 / 2 忽略**
   （确认本件给 `Cargo.toml` 加的 `[[bench]]` 没碰坏任何守卫，含
   `build_id_guard::the_crate_version_is_deliberately_zero_and_the_real_identity_has_a_home`）。
   **那是后端一棵树的读数，不是全仓门禁全绿的证明** —— 前端那半本件一个字没动、也没跑。
