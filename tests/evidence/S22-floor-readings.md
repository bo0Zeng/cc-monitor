## ② 它在防什么？—— 真浏览器实测

### 2.1 规范怎么说

`contain-intrinsic-size` 的形式语法是 `[ auto? [ none | <length [0,∞]> ] ]{1,2}`
（CSS Box Sizing 4 / MDN `contain-intrinsic-size` 的 Formal syntax）。
⇒ **0 合法，负值非法，规范没有任何"最小值"夹取。**
`auto` 关键字的含义是「元素**正常渲染过**之后，用记住的真实尺寸，否则才用声明的 `<length>`」。

### 2.2 两个引擎实测（B 段，5 个 class × 18 个声明值 = 90 行/引擎）

视口外、从没渲染过的卡，inline 写 `auto <D>px`，读 `getBoundingClientRect().height`：

| 声明 | Chromium measured | WebKitGTK measured | effective（= measured − padBorder） |
|---|---|---|---|
| 无 inline（CSS `auto 120px`） | 126.00 | 126.00 | 120 |
| `auto -1px` | **126.00** | **126.00** | **120 ← 声明被丢弃，computed 回落到 CSS 的 `auto 120px`** |
| `auto 0px` | 6.00 | 6.00 | **0** |
| `auto 1px` | 7.00 | 7.00 | 1 |
| `auto 2/3/4/5/6/8/10/12/16px` | 8/9/10/11/12/14/16/18/22 | 同 | 逐位 = 声明值 |
| `auto 17px` | 23.00 | 23.00 | 17 |
| `auto 24px` | 30.00 | 30.00 | 24 |
| `auto 120px` | 126.00 | 126.00 | 120 |

（表里是 `card-api-retry`，padBorder = 6。另外四个 class 同样「所有 ≥0 声明值 effective == declared」，
padBorder 分别是 bash-input 12 / slash 12 / user 22 / assistant 0。）

**三条结论，两个引擎逐位一致：**

1. **盒模型是 content-box** —— 声明 N ⇒ 实际占 N + padding + border。（这一条复核了
   `height-estimate.ts:294` 的自陈，也复核了秤 2 B 段的旧读数。）
2. **两个引擎都没有下限夹取**：0 就是 0，1 就是 1。`CSS.supports("contain-intrinsic-size","auto 0px")`
   两边都 `true`。
3. 🔴 **负值不会变成 0，而是整条声明被丢弃 ⇒ 静默落回 CSS 的 `auto 120px`。**
   `CSS.supports(..., "auto -1px")` 两边都 `false`。
   ⇒ 注释说的「防负值」，**地板在这件事上根本不起作用也不需要起作用**：
   就算真写出负值，浏览器给的不是 0 而是 120（一个**更大**的虚高值，不是塌陷）。

### 2.3 `auto` 真的记得住吗（C 段）—— 决定地板的爆炸半径

一张 `card-api-retry`，先在视口外量、滚进视口渲染一次、再滚出去量：

| declared | 引擎 | 首次 skipped | 渲染时 | 再 skipped | 记住了？ |
|---|---|---|---|---|---|
| 0px | Chromium | 6.00 | 23.05 | **23.05** | ✅ |
| 0px | WebKitGTK | 6.00 | 23.00 | **23.00** | ✅ |
| 17px | 两个 | 23.00 | 23.05 / 23.00 | 23.05 / 23.00 | ✅ |
| 24px | 两个 | 30.00 | 23.05 / 23.00 | **23.05 / 23.00** | ✅ |

⇒ **两个引擎都实现了 last-remembered-size。**
地板（以及任何估值误差）**只影响「从没渲染过的卡」贡献的首屏几何**，
卡一旦被滚过一次，声明值就再也不起作用了。这也说明 `contain-intrinsic-size` 写错
**不会造成正确性问题**，只造成滚动条/跳转的几何误差 —— 这一点与模块头注的自陈一致，现在是实测的。

⚠ `checkVisibility({contentVisibilityAuto:true})` 在**两个引擎上都恒返回 "未 skip"**
（`skipped=false`），与高度读数矛盾。这个标志**不可信**，本报告一律以高度为准
（`auto 0px` 读到 6.00 而不是真高 23.05，只可能是 size containment 生效）。

## ④ 🔴 判断：**地板应当降到 17，或者直接去掉；不该留在 24**

三种可能逐条给代价。

### 方案 ① 降到某个数（**推荐：17**）

改 `height-estimate.ts:343` 的 `Math.max(24, …)` → `Math.max(17, …)`。

- **收益（实测，见 ⑤ 的表）**：`card-api-retry` p90 40.8% → **0.3%**；
  `card-bash-input` 29.1% → **2.2%**；`card-slash` 29.1% → **2.2%**，
  且 WebKitGTK 上 `card-slash` 那个**已经超过设计门槛的 33.3%** → **5.6%**；
  `card-user` 10.7% → **1.4%**。`EXCEEDS_DESIGN_GATE` 从 2 条缩到 **1 条**（只剩 `card-api-error`）。
- **代价 A（真实但小）**：17 是**今天盘上**的下界。将来若出现一个真高 < 17 的卡型
  （例如更小字号的细条），17 会重新变成"顶起来"的地板 —— 和今天的 24 同一个病，只是小了 7px。
- **代价 B（今天为零）**：17 与"没有地板"在今天这份语料上**逐位相同**
  （估值最小值就是 17）。⇒ 选 17 而不是 0，买到的不是精度，是"未来某个 bug 返回 0 时
  不会塌成 0"这一点点保险。地板 8 / 10 / 17 三档在今天的 p90 表上**一模一样**。
- **代价 C（改一个数要动五处，这是最大的一笔）**：

  | # | 住址 | 要做什么 |
  |---|---|---|
  | 1 | `src/height-estimate.ts:343` | 地板本体 `Math.max(24, …)` |
  | 2 | `tests/scale2-height-truth.vitest.ts:84` | 硬写的 `const APPLIED_FLOOR = 24` |
  | 3 | `tests/evidence/U-scale2-probe-entry.ts:49` | 又一份硬写的 `const APPLIED_FLOOR = 24` |
  | 4 | `tests/scale2-height-truth.vitest.ts` 的 `P90_CEILING` / `EXCEEDS_DESIGN_GATE` | 上限往下棘，把 `card-api-retry` 从超标名单里删掉 —— 这一步**会红一次**，那是登记制度想要的 |
  | 5 | 🔴 `tests/scale2-height-truth.vitest.ts:455–540`（「悬案③ · 一屏门控三段边界」） | **整段的前提是「视口外每张 retry 实际占 30px」**（= 地板 24 + padding 6）。地板改 17 之后前提变成 **23.05**，红带 `[14,17] ∪ [27,34]` 与「18–26 最稳」那几条结论全要重算。 |

  ⚠ 第 5 处**不会自己红**：它的 `estH` 是从金标准的 `intrinsic[declared===24]` 那一格读的，
  不是从 `APPLIED_FLOOR` 读的 ⇒ 地板改了它照样绿，**只是从此在量一个不再出货的配置**。
  那一段自己的注释已经写明「哪天地板动了，这一整段要跟着重算」——
  改地板的人必须回来兑现这句话，否则就是一把安静变坏的尺子。

### 方案 ② 整个去掉

直接 `auto ${Math.round(h)}px`。

- **收益**：与 17 完全相同（今天逐位一致），少一个没有出处的魔数。
- **代价 A（实测可判）**：负值写不出来（②·2.5 的代码面核对 + 全项非负）；
  就算写出来，浏览器**丢弃整条声明并回落到 CSS 的 120px**（②·2.2 实测），
  是虚高不是塌陷 ⇒ **没有"塌成 0"这个风险**。
- **代价 B（实测可判）**：0 只有 `card-user` 空正文一条路，而 `renderMessage` 不给空正文建卡
  （②·2.5 实测）⇒ **今天不可达**。
- **代价 C（判不了，这是唯一真风险）**：将来新加卡型时，估高函数可能因为选择器写错
  返回一个接近 0 的数。没有地板时它会写 `auto 0px`（实测：总高低估 28.5%/50.3%、
  滚动条抖 2335/4114px、Chromium 跳转落点差 1535px、WebKit 滚位被顶走 202px）；
  有 17 的地板时最坏也只低估到 17。**这一格是"对未来 bug 的保险"，不是对今天任何一张卡的保护。**

### 方案 ③ 按 class 分档

给每个 class 各配一个下限。

- **收益**：理论上最紧。
- **代价（大，且是坏结构）**：`applyIntrinsicSize` 只拿得到 `HTMLElement`，
  要分档就得在它里面**再做一次 class 判定** —— 而 class 判定已经整套住在
  `estimateStreamNodeHeight` 里了。⇒ 同一份 class 知识落两处，
  下次加卡型要改两个地方，正是 `设计/17 §2.2` 那条"下次加新卡型又静默落回兜底"的复发形状。
- **而且它解决的问题不存在**：分档下限的正确值，就是各 class 常数本身
  （17/19/19/…），而那些常数**已经是** `estimateStreamNodeHeight` 的返回值。
  ⇒ 分档等于把常数抄第二遍。**不推荐。**

### 一句话

> **把 `Math.max(24, …)` 改成 `Math.max(17, …)`，并把方案 ① 代价 C 那张表的五处一起兑现。**
> 理由：24 的出处是一个已被判错的 border-box 手算值；它自陈防的两件事（0 / 负值）一个不可达、
> 一个浏览器自己拒；而它在两个真引擎上都让重试风暴的滚动几何**变坏 20%+**。
> 17 = 今天盘上实测的最矮卡真高（两个引擎 17.05 / 17.00），在今天这份语料上与"无地板"等价，
> 但保留了一点对未来 bug 的保险。

## ⑥ 这份读数量不到什么（不完整本身就是缺陷）

1. **真高是"这台 Linux 无头机 + 这套 fallback 字体"的真高**，不是生产 Windows WebView2 的真高。
   与秤 2 同一个缺口，没有改善。
2. **`card-api-retry` / `card-slash` / `card-bash-input` 的语料是手工构造的**
   （真机 32 674 条记录里这几个卡型 0 条 / 0 条 / 2 条，见 `tests/scale2-height-corpus.ts` 头注）。
   ⇒ 「17.05 是 `card-api-retry` 的真高」带着"构造体长得像不像真的"这个前提。
   但 CSS 是 `white-space: nowrap; overflow: hidden` ⇒ **再长的文案也只有一行**，
   这一条把前提的风险压得很小。
3. **D 段的重试风暴是合成的**（同一张卡 clone 300 次）。真实风暴里卡型会混杂。
4. **没量"一次强制布局多少钱"**（`设计/17 §5` 第 2 条），也没量改地板对
   `materializeUntilFilled` 补批轮次的影响（那归秤 3）。
5. `checkVisibility({contentVisibilityAuto:true})` 两个引擎都不可信（见 ②·2.3），
   本报告一律以高度读数为准；**"到底 skip 没 skip"这一格没有独立证据**。
6. 本轮跑的时候工作树里有另一路在飞的 `src/styles.css` 重构。三次独立跑真高一个数都没变，
   且与另一树状态下打的金标准逐位相同 ⇒ 判为未受影响；但**这不是证明**。
