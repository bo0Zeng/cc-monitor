## 0. 装表法：**一行 `src/` 都没改**

### 0.1 为什么不照文档给的装表法

§6 表里写的是「`events.ts:368` 与 `:402` 后加一行 `perf.queueMax = Math.max(...)`」。
**这份读数没走那条路**（`src/events.ts` 不在本次的写区，且正被别人改）。改走纯外部观测。

### 0.2 外部怎么量到一个闭包私有的 `queue`

`bindEvents` 里的 `const queue: QueueItem[] = []` 外面拿不到，但队列是 FIFO 而**两端都在测试手里**：

| 端 | 怎么观测到 |
|---|---|
| 入队 | 喂 `jsonl-batch` 事件的人就是测试自己 ⇒ 每条 push 的 kind / 时刻逐条可知 |
| 出队 | `bindEvents` 收的 `EventHandlers` 全是测试的假 handler ⇒ `onLine` 调用次数 = **payload 条目**出队数 |

⇒ `queue.length(t) = 已 push(t) − 已 dispatch(t)`。

**哨兵这一半是有误差的，读数里没藏：**

- `batch-start`：**精确可观测**。它出队时走 `enterBatchMode()` → 调 `onBatchStart`；
  且本读数每条流里 `batch-start` 只有一个（只在 `chunkIndex===0` 时 push）。
- `batch-end`：**不可直接观测**。它出队时只调 `scheduleBatchEnd()`（排一个 300ms 定时器），
  没有任何 handler 被调。

但误差有硬上界：喂进去的流里**任意两个哨兵都不相邻**
（chunk0 = `[batch-start, payload×k, batch-end]`，chunk i>0 = `[payload×k, batch-end]`，每块 k ≥ 1），
所以由 `onLine` 次数反演出的「已 dispatch 条目数」是一个**宽度 ≤ 1 的区间**。
下表里每个深度都写成 `[lo, hi]`，`hi − lo ≤ 1` 由判据①机检（宽度一破它先红）。

**结论：峰值不是一个编出来的确数，是一个宽度 ≤ 1 的区间。** 表里「峰值/输入」那一列用的是上界 `hi`。

### 0.3 ⚠ 让出机制：本读数**把 drain 的让出逼到 `setTimeout` 兜底那一支**

`events.ts` 的 `makeYieldToMain` 会**特性探测** `MessageChannel`：探到就用它让出
（宏任务，且规范没给它嵌套 timer 那条 4ms 钳制），探不到才退回 `setTimeout(run, 0)`。
jsdom **有** `MessageChannel`，而假定时器**驱动不了它** ⇒ 不干预的话队列一条都排不出来
（实测：`onLine` 恒 0）。所以判据在 `bindEvents` **之前**做
`vi.stubGlobal("MessageChannel", undefined)`，把它逼回那条**生产上真实存在**的兜底路。

**这决定了读数的适用范围：下面的表量的是 `setTimeout` 兜底那条路。**
`MessageChannel` 那条路没有 4ms 钳制、让出更密 ⇒ 同样输入下峰值只会**更低**，
低多少取决于真 handler 的每条成本 —— **那个这份读数没测**（handler 是 `vi.fn()` 空壳）。

判据里有一格自检专治这件事：第一块推完后如果一个假定时器都没有，
它会带着「让出机制不再走 `setTimeout` 兜底了，驱动方式要重做」这句话红掉，
而不是退化成一条指不出原因的 `onLine=0`。

### 「gap 内 drain」那一列是**模型参数，不是测出来的**

## 4. 两个结构性发现

### (1) 在 `setTimeout` 兜底那条让出路上，前端 drain 追不上后端推送 ⇒ 峰值 ≈ 全量条数

后端一块 600 条、块间 10ms；前端一个 drain tick 至多 `BATCH_SIZE = 40` 条
（`events.ts` 里 `isInputPending` 探不到时走的固定预算，jsdom / WebKitGTK 都是这条）。
要追平，一个让出 tick 得比 `10ms ÷ (600/40) = 0.67ms` 还快 —— `setTimeout` 的钳位下限是 1ms、
嵌套深了 4ms，**三档 pacing 里没有一档追得平**。

实测：三档下「推完第 i 个**满块**」的深度逐块严格变大（判据⑥机检），
峰值恒落在某次 push 刚完成的时刻（判据⑦），比值 `峰值/输入` = 0.35 ~ 1.00。

唯一会回落的地方是**最后一块**：`build_chunks` 是**从尾往前切**的（`event_replay.rs:441`），
余数落在最后一块（4566→366、13081→481、20000→200）。余块比一个 gap 的 drain 配额还小时深度本来就该落
—— `pacing=10 / total=20000` 的峰值正是落在第 **32** 块而不是第 33 块，`4566` 落在第 **6** 块。
判据⑥把余块显式排除，并在注释里写明**这是物理而不是为了让判据变绿**。

> ⚠ **这条结论只覆盖 `setTimeout` 兜底路。** 另一路 agent 正在换成 `MessageChannel` 让出
> （没有 4ms 钳制），那条路上「追不追得上」取决于真 handler 的每条成本，
> **这份读数没测**（见 §0.3 / §5「没答」第 1 条）。

### (2) §2.10 的「超线性」有一道**很陡而且很窄**的坎，位置在 15000–15300 之间

B 表里 13081（0.658 ms）比 4566（0.726 ms）还**快**一点 —— 不是噪声。
补跑的坎位扫描（`node` 直跑，不在判据文件里，属旁证）：

```
升序：                      降序（同一进程复测）：
 13081     0.585             20000    12.307
 14000     0.614             16000     8.030
 14500     0.635             15300     7.309
 15000     0.657             15000     0.658
 15300     7.296             14500     0.635
 16000     7.943             14000     0.613
 20000    12.440             13081     0.572
```

**n 涨 2%（15000 → 15300），耗时涨 11×**，且升降序复测位置一致（不是热身/JIT 假象）。
这正是 §2.10 那句「V8 的 left-trim 快路不是无条件生效」——坎两侧是两条不同的复杂度曲线，
中间几乎没有过渡带。

⚠ 坎的位置**盯的是 backing store 的容量而不是 `length`**（`push` 的容量增长是几何的，
容量 ≥ length），所以它**不是 n 的干净函数**，换 V8 版本 / 换指针压缩开关
（本机 `v8_enable_pointer_compression=0`）就会挪。
**别把「15000」当常数抄进设计文档**；能抄的是「坎存在、很陡、就在这个量级附近」。

## 5. 这份读数**答了什么** / **没答什么**

### 答了

1. **队列峰值随输入线性长，量级 ≈ 全量条数的 0.35 ~ 1.00 倍**（`setTimeout` 兜底路），
   不会被任何机制压在「一块（600 条）」上。
2. **后端那一侧的分块形状是确定的**，常数都引到住址了，且由判据 C **机检没漂**（读文件，不改）：
   - `src/bridge/src/event_replay.rs:48` — `const CHUNK_SIZE: usize = 600;`
   - `src/bridge/src/event_replay.rs:47` — `const SINGLE_CHUNK_THRESHOLD: usize = 200;`（低于它后端**不切块**，单块 emit，见 `:216`）
   - `src/bridge/src/event_replay.rs:50` — `const CHUNK_PAUSE_MS: u64 = 10;`
   - `src/events.ts` 的 `const BATCH_SIZE = 40;`（判据 C 用正则抽，不钉行号 —— 那份文件正在被改）
3. **`shift()` 的超线性是真的，而且是一道窄坎**，本机 node v22 上落在 15000–15300 之间（§4(2)）。
4. **「换头指针是等价替换」这句话成立**：四个档位上两条路排出来的元素序列逐条一致（B 唯一的断言）。

### 没答（**逐条明说，不推断**）

1. **这是 jsdom + fake timers 下的读数，不是真机 WebView2。** 具体四条：
   - **让出机制被我按到了兜底路上**：判据 `vi.stubGlobal("MessageChannel", undefined)`，
     量的是 `setTimeout(drain, 0)` 那一支。两个生产壳（WebView2 / WebKitGTK）按 `events.ts`
     的注释都**有** `MessageChannel` ⇒ **真机走的大概率是另一支**，那支没有 4ms 钳制、
     让出更密、峰值更低。**低多少没测。**
   - **定时器是假的**：drain tick 由 `vi.advanceTimersToNextTimerAsync()` 一个一个手动放行；
     「10ms 的 chunk 间隔里到底跑得完几个 tick」**没测**，是那个 pacing 旋钮。
   - **JS 引擎不是同一个**：node v22 的 V8 ≠ WebView2 的 V8，**§4(2) 那道坎的位置几乎肯定不一样**。
   - **handler 是 `vi.fn()` 空壳**：真机上 `onLine` 要走 `RecordTimeline` 建卡 / 分支计算，
     每条成本高几个数量级 ⇒ 会让 drain 更慢、队列更深。**这个方向的偏差没量**，
     而它和上面第一条是**反向**的，净效果朝哪边都说不了。
   - 另：payload 是 5 个字段的假对象，真 payload 的大小/结构不同。

2. **真机上「28 会话全量重放」到底喂多少条 payload、分几个 chunk —— 这个数我没有。**
   - **chunk 大小常数找到了**（`event_replay.rs:48` = 600，地址与数值见上），但
     **总条数 N 在代码里不是一个常数**：它等于 `EventReplay.inner.history` 的长度
     （`event_replay.rs:30` 那个 `VecDeque`），由 watcher 的首次全量扫一行一行 `push_back` 填满，
     **全文件没有任何上限 / 环形截断**（grep `MAX_HISTORY` / `pop_front` / `truncate` 均无命中；
     只有 `:321` 用户主动关 Tab 时的 `retain` 会删）。⇒ **峰值没有任何后端上限兜着，N 有多大峰值就有多大。**
   - 另：任务书里说的 `src/backend/` 这个目录**不存在**，后端在 `src/bridge/`
     （其下另有一个 `src/bridge/src/backend/` 子目录，不是 replay 逻辑所在）。
   - 旁证（**弱，不是答案**）：本机 `~/.claude/projects` 下 131 个 `.jsonl` 共 **53170** 行，均 ~406 行/文件。
     若 28 个会话都按这个均值算，N ≈ 11400 —— **正好压在那道坎的下方一点点**。
     但这三件事一件都没验：① 哪些会话算「active」（watcher 只 tail 活跃 jsonl）；
     ② 每一行 jsonl 是不是都变成一条 payload；③ 这台机器的语料是不是那台机器的
     （本机 131 个文件**近 7 天一个都没动过**）。**所以这个 11400 不能当结论用。**

3. **§2.10 那两个数：量级复现了，倍数没复现。**

   | | §2.10 现打 | 本次（node v22 / jsdom，5 次） | 判 |
   |---|---|---|---|
   | n=4566 shift() | 0.83 ms | 0.64 ~ 0.93 ms | **量级对上** |
   | n=4566 头指针 | 0.042 ms | 0.020 ~ 0.094 ms | 量级对上 |
   | n=4566 倍数 | 20× | 7 ~ 39×（抖得厉害） | 量级对上 |
   | n=20000 shift() | 15.64 ms | 12.5 ~ 18.2 ms | **量级对上** |
   | n=20000 倍数 | 290× | 106 ~ 154× | **对不上，差 ~2×** |

   倍数对不上出在**分母**：§2.10 隐含的 n=20000 头指针耗时是 `15.64/290 ≈ 0.054 ms`，
   本次实测 0.094 ~ 0.136 ms。分子（真正要命的那一半）两档都复现了。
   §6 表里还给了一个 `n=13081 → 2.2 ms`，**这个没复现** —— 本次 13081 实测 0.57 ~ 0.83 ms，
   比它小约 3 倍，而且 13081 在本机**落在坎的下方**（§4(2)）。

4. **这份读数量的是队列深度，不是「重放到底卡不卡」。**
   深度 → 卡顿之间还隔着：真 handler 的每条成本、DOM 建卡、主线程让出的真实粒度、
   用户什么时候开始点。`17 §5` 把这些列进「分不清」，**这里一条都没答，也没替它们下结论**。

## 6. 结论（一句话）

**判不了 —— 但判不了的原因收窄到了一个具体的数。**

队列峰值 ≈ 全量条数（`setTimeout` 兜底路、pacing=2 档下是 0.87 × N），
而 `shift()` 的代价在 N 越过一道**很陡的坎**（本机 15000–15300）时从 ~0.6 ms 跳到 ~8 ms 以上。
⇒ §2.10 落在「可忽略」还是「不可忽略」，**完全取决于真机重放的 N 落在坎的哪一侧**，
